## 1. 서비스 범위

이 문서의 **MVP는 실제 런칭을 목표로 하는 첫 출시 범위**다. 2026-11-25를 해당 범위의 구현 목표로 두며, 발표용 시연만을 목표로 하지 않는다. 주요 화면의 1차 퍼블리싱과 목업 상호작용을 구현했고, 백엔드 업무 API 구현과 프론트 연동을 기능별로 함께 진행하는 단계다. 미구현 요구사항과 화면별 세부 조정은 남아 있으며, 전체 반응형·접근성·실제 서버 연동의 완료를 뜻하지 않는다. 기능별 백엔드 API 구현과 프론트 연결을 함께 진행하고 저장 유지·권한·실패 처리를 확인한 뒤, 구현·연동 결과에서 ERD와 API 명세서를 정리한다. 기존 ERD는 참고 검토본이며 데이터 관계·중복 제약·요청/응답은 해당 기능을 개발하기 전에 맞춘다. ERD는 최신 정책·기술 구성과 대조한 현행 검토본이며 물리 설계 확정과 업무 API 검증은 남아 있다. 개발 단계·기술·운영 상태는 기획서 1장과 `PROJECT_CONTEXT.md`를 따른다.

#### 2.1.1 현재 인증·회원 구현 기준

- 구글 OIDC 범위는 `openid email`이며, 인증 후 `WEBTER_SESSION` 쿠키(HttpOnly, SameSite=Lax)로 서버 세션을 사용한다. 구글 토큰은 보관하지 않고 검증된 이메일만 비공개 회원 정보로 저장한다. 구글 프로필 사진은 수집하지 않는다.
- 구글 인증 직후 미가입 사용자는 DB에 저장하지 않고 가입 대기 세션만 둔다. 최종 제출에서 회원·구글 계정 연결·현재 약관 3종의 동의 이력·관심 카테고리를 한 트랜잭션으로 저장한다. 로그인 상태는 비회원·가입 대기·회원으로 구분한다.
- 변경 요청은 CSRF 토큰 헤더를 요구하며 로그인/가입 시 세션 ID를 교체한다. 로그아웃·탈퇴 시 현재 세션을 무효화한다. 현재 세션 만료는 비활동 30분(환경변수로 조정)이며 운영 정책 확정을 뜻하지 않는다.
- 계정 설정·탈퇴와 프론트 연결을 구현했다. 서비스·리뷰·댓글·알림·좋아요·저장 등의 실제 업무 API 연결 완료를 뜻하지 않는다. API와 환경변수는 `BE/README.md`, 프론트 연결과 개발 도구는 `FE/README.md`를 따른다.
- 현재 계정 설정 API는 아이디·닉네임·소개(80자)·외부 링크(유형별 1개·최대 5개)·관심 카테고리(최대 3개)를 함께 저장한다. 프로필 사진 서버 저장과 아이디 변경 이력 적용은 별도 구현이 필요하다.
- 운영 도메인은 구매하고 서브도메인 구조로 정했으며 쿠키 전달 세부는 구현 때 정한다. 서버 렌더링 로그인 복원, 세션 만료 안내와 제재 회원 로그인 차단은 미정 또는 후속 작업이다. 운영 유지 기간을 30분으로 확정한 것이 아니다.
- 아이디 변경 14일 2회 제한은 이전 "제한 미정" 문구보다 최신이다. 업무 목업은 인증 계정 탈퇴만으로 실제 삭제·집계가 연결되지 않는다.
- 새 닉네임 규칙은 FE·BE 검증, 길이 표시·안내, 자동 테스트에 적용했다(2026-11-04). 예: `사과먹는 개발자`는 15칸으로 허용, `사과먹는 개발자님`은 17칸으로 불가, `사과먹는개발자님`은 16칸으로 허용한다.

## 3. 권한

아래 회원은 온보딩 최종 제출을 마쳐 가입이 완료된 회원이다. 구글 인증만 성공한 사용자는 회원 권한을 얻지 않는다. 백엔드는 화면 버튼 표시와 별개로 가입 완료·계정 제재·소유권·알림 수신자·초대 수신자를 확인한다. 수락한 팀원은 등록자와 같은 권한(서비스 관리·수정·삭제, 버전 기록, 팀원 초대·삭제, 등록자 제거)을 가진다. 팀원이 남은 서비스는 등록자가 탈퇴해도 유지하고 가장 먼저 수락한 팀원이 등록자 자리를 잇는다(4.11). 공개 여부와 권한은 대상별로 검증한다.

### 4.3 서비스 상태

서비스에는 두 종류의 상태가 있다.

| 상태 | 값 | 변경 주체 | 규칙 | 구분 |
|---|---|---|---|---|
| 운영 상태 | 운영 중 / 운영 중지 | 등록자와 수락한 팀원 | 운영 중지 전환 시 사유를 입력하고 상세에 표시한다. 이용하기는 비활성화하며 홈·공개 탐색의 기본 목록은 운영 중만 표시한다. 필터로 운영 중지를 포함할 수 있다. 본인·저장 목록은 운영 중지도 기본 포함한다. 운영 중지에서도 좋아요·저장과 미설정 리뷰는 가능하나 단독 추천·비추천은 불가하다 | 확정 |
| 공개 상태 | 공개 / 비공개(임시 비공개 포함) | 관리자, 자동 임시 비공개 | 등록 즉시 공개한다. 「공개」일 때는 어떤 화면에도 표시하지 않는다. 「비공개」(임시 비공개 포함)일 때만 비공개 상태임과 사유를 표시하며, 표시되는 곳은 등록자의 내 서비스 관리와 마이페이지다. 일반 사용자는 비공개 서비스를 목록·검색·상세 어디에서도 볼 수 없다. 등록자는 상태를 바꿀 수 없다 | 확정 |

비공개 전환 시 WEBTER가 제공하는 해당 서비스 이미지의 **새 요청도 접근 제한 대상**이다. 저장·전송·임시 URL·캐시 정책과 반영 시간은 미정이며, 이미 다운로드되거나 외부 SNS 등에 저장된 사본의 회수는 보장하지 않는다(4.4).

배포 전·출시 예정 상태는 두지 않는다.

등록자가 자기 서비스를 직접 비공개로 바꾸고 다시 공개로 되돌리는 기능은 **확장**이다(11). 관리자가 건 비공개와 등록자가 건 비공개는 구분해야 하며 구분 방식은 확장 때 정한다. 공개 상태 필드는 DB 설계에 MVP부터 포함한다. 구분: 확정

### 4.4 이미지

**1차 연동에서 이미지 업로드를 S3로 구현한다(M-77).** 비공개 버킷에 CloudFront를 앞에 두고 브라우저가 일회용 주소로 직접 올리며, 백업용 버킷과 분리한다. 용량·형식은 업로드 주소를 발급할 때 제한하고 실제 이미지 여부와 유해성은 업로드 뒤 서버가 확인한다. DB는 이미지 주소 문자열을 보관하므로 별도 이미지 저장 구조를 새로 만들지 않는다. 현재 화면의 파일 선택·미리보기는 서버 업로드와 연결하기 전 상태다.

저장소는 S3로 확정했다. 임시 URL·캐시·비공개 이미지의 새 요청 제한 세부는 미정이다. 아래 이미지 종류·표시·형식 규칙은 업로드 연결 시 적용하며 현재 업로드 API 구현 완료를 뜻하지 않는다.

| 종류 | 용도 | 규칙 |
|---|---|---|
| 아이콘 | 목록형 보기, 이후 다른 화면에서도 사용 가능 | 정사각형, 512×512 이상 권장 |
| 썸네일 | 카드형 보기 | 카드 비율로 잘라서 등록 |
| 미리보기 | 상세 페이지 | 최대 8장. 서비스 단위로 가로 16:9 또는 세로 9:16 중 하나를 선택하고 모든 이미지를 같은 비율로 통일한다. 이미지 맞춤은 "꽉 채우기"(가운데 기준 자동 맞춤) 또는 "전체 보이기"(비율 유지, 남는 곳은 여백) 중 선택. 직접 크롭·위치 조정 도입은 미정 |

- 세 이미지 모두 선택 입력이다. 아이콘과 썸네일을 올리지 않으면 선택한 서비스 용도별 기본 이미지를 보여 주고, 미리보기를 올리지 않으면 해당 영역은 생략한다. 정확한 카드 비율은 화면 디자인에서 정한다.
- 업로드 형식은 JPG, PNG, WebP이고 장당 5MB 이하이다. 5MB를 넘는 이미지는 거절하지 않고 올리기 전에 브라우저에서 자동 압축한다(아이콘은 적극적으로, 서비스 화면의 썸네일·미리보기는 약하게). 너무 큰 원본은 입력 상한으로 거절하고 압축 후에도 5MB를 넘으면 안내하며, 사용자는 확대 미리보기로 압축 결과를 확인한다. 서버는 형식·용량을 다시 검증하며 브라우저 압축이 서버 검증을 대체하지 않는다. 부적절한 이미지는 신고·운영 조치와 등록 후 AI 유해성 검사 방향에 따라 처리한다(8·10). 구분: 확정(형식·용량·압축 방식·검사 방향), 미정(압축 수치·입력 상한·검사 세부)
- 비공개 서비스 이미지의 새 요청도 제한한다. 이미지 저장소·전송 방식, 임시 URL 유효기간, 캐시 정책과 반영 시간은 미정이다. 이미 내려받거나 외부에 저장된 사본의 회수까지 보장하지 않는다.

### 4.5 버전 기록

서비스별로 업데이트 이력을 남길 수 있다. 등록자가 버전, 제목, 내용을 입력하고 일자는 등록 일시가 자동으로 입력된다. 등록자가 수정·삭제할 수 있고, 최초 등록 일시는 유지한다. 상세 페이지에서는 눈에 띄지 않게 하단에 두며 앱스토어처럼 존재만 하게 한다. 구분: 확정

### 4.6 삭제

서비스를 삭제하면 해당 서비스의 리뷰·제작자 답글·댓글·버전 기록·좋아요·저장도 함께 삭제한다. 구분: 확정

신고·운영 기록 등은 현행 DB의 보존 규칙과 운영 보관 정책을 따르며 별도 확인한다.

### 4.7 등록 개수 제한

한 계정은 하루에 서비스를 **5개까지** 등록할 수 있다. 총 등록 개수는 제한하지 않는다. 구분: 확정(방식·수치, M-75)

현재 프론트 목업 상수는 3개이므로 서버·프론트 연동 시 확정값을 반영해야 한다. 날짜 경계 등 세부 집계 방식은 구현에서 맞춘다.

### 4.8 서비스 용도 카테고리와 태그

서비스 용도는 "무엇을 하려고 들어가는가"라는 사용 목적을 기준으로 나눈다. 기술(AI 등), 형태, 가격은 카테고리에 섞지 않는다. 카테고리는 한 단계만 두고, 세부 분류는 태그가 맡는다.

하위 세분화 카테고리는 확장 아이디어로 기획서 11.2에서 검토한다. 게임의 메타버스·힐링·공포와 팀전/개인 같은 예시는 장르·경험·참여 방식이 섞여 있으므로 최종 계층이나 필수 등록 항목으로 확정하지 않는다. 도입 전에는 위 한 단계 구조와 태그 규칙을 유지한다.

| # | 카테고리 | 예시 |
|---|---|---|
| 1 | 놀이 | 웹게임, 퍼즐, 퀴즈, 룰렛, 심리테스트 |
| 2 | 일상 | 여행, 음식, 지도, 돈 관리 |
| 3 | 학습 | 단어장, 공부 도구, 학습 게임 |
| 4 | 업무 | 할 일, 타이머, 문서·일정 |
| 5 | 창작 | 이미지 편집, 색상, 그림, 음악 |
| 6 | 간편 도구 | 변환·계산·파일 같은 작은 도구 |
| 7 | 개발 도구 | API 테스트, 코드 도구 |
| 8 | 기타 | 위에 맞지 않는 서비스 |

- 홈, 목록 위 카테고리 줄, 사이드바, 등록 화면에는 위 순서로 표시한다.
- 서비스는 카테고리를 복수로 선택할 수 있다(최대 3개는 제안). 첫 번째로 고른 카테고리가 대표 카테고리이며 기본 이미지에 쓴다. 필터와 관심 카테고리는 선택한 카테고리 중 하나라도 해당하면 서비스를 보여 준다.
- 소분류는 두지 않고 태그(자유 입력, 최대 5개)가 그 역할을 한다.
- 태그 추천(확장, MVP 아님): 등록할 때 서비스 이름, 설명, 선택한 카테고리를 보고 알맞은 태그를 추천한다(네이버 지식인의 카테고리 추천처럼). 등록자가 추천된 태그를 고르거나 직접 입력한다. 기존에 쓰인 태그 중 글자가 맞는 것을 추천하는 규칙 방식을 기본으로 하고, AI 방식은 확장으로 둔다.

구분: 확정(목록·순서·복수 선택, 태그 추천은 확장), 제안(최대 3개, 태그 추천 방식)

### 4.9 이용 형태와 지원 언어

서비스를 어떻게 이용할 수 있는지(이용 형태)와 서비스가 지원하는 언어를 분류에 포함한다.

| 기준 | 값 | 규칙 |
|---|---|---|
| 이용 형태 | 웹 서비스 / 오픈소스(확장) / (확장) 사이트 안에서 이용 | 서비스 링크가 있으면 "웹 서비스", GitHub 링크만 있으면 "오픈소스"(확장)이다. 웹 서비스에 GitHub 링크를 함께 입력하면 코드 아이콘이 표시되며, 이용 형태는 "웹 서비스"로 유지된다 |
| 지원 언어 | 한국어 / 영어 | 복수 선택, 기본값은 한국어. 서비스가 지원하는 언어이며 WEBTER 화면의 언어와는 별개 |

- 상세 페이지에는 `이용하기` 버튼(서비스 링크)을 두고, GitHub 링크가 있으면 코드 아이콘(`</>`)만 둔다. 사용자가 바로 즐기는 것이 WEBTER의 목적이므로 GitHub 연결은 눈에 띄지 않게 둔다. 제작자 본인의 GitHub 계정은 프로필의 외부 링크에, 서비스의 소스 저장소는 서비스 상세 페이지에 둔다.
- 필터에서 지원 언어로 서비스를 거를 수 있다. 이용 형태는 지금 고를 수 있는 값이 없으므로 필터로 두지 않는다. 모든 서비스에 같은 웹 서비스 항목은 현재 상세에서 생략한다.
- 내부 연결(확장)을 도입하면 상세 페이지에 설명 탭(미리보기 이미지)과 이용 탭(사이트 화면)을 두고 전환한다.

구분: 확정

### 4.10 오픈소스 서비스 (런칭 이후 확장)

독립 영역은 시연 때까지 구현하지 않고 런칭 이후 다시 검토한다. 현재 프론트의 헤더 진입점·라우트·샘플은 제거했다. 아래 항목은 확장 시 검토할 방향이며 일반 웹 서비스의 GitHub 소스 링크는 유지한다.

GitHub 링크만 있고 서비스 링크가 없는 서비스를 "오픈소스"로 받는다. 라이브러리, 도구 등 GitHub로 소스가 공개된 프로젝트가 해당한다. 개발자가 모이는 곳이라 수요가 없다고 할 수 없지만 일반 사용자에게는 낯설어서, 메인 기능이 아니라 옆으로 빼 둔 부가 영역으로 둔다. MVP는 아니다.

- **입구(확장 검토):** 별도 코드 아이콘 진입을 검토한다. 현재 헤더에는 이 진입점이 없다.
- **영역 안:** 트렌딩·인기·최신과 카테고리로 탐색한다.
- **기본 노출:** 홈, 기본 목록, 검색에서는 오픈소스를 제외한다. 검색 필터에서 사용자가 직접 설정하면 오픈소스를 포함한다(이용 형태 필터를 두지 않으므로 포함 방식은 확장 때 다시 정한다).
- **버튼:** `이용하기`가 없고 GitHub 저장소로 연결한다.
- **집계 분리:** 오픈소스는 이용 집계를 하지 않는다. 실행 기준이 모호하기 때문이다. 좋아요와 저장만으로 인기 순위를 매기고(점수 = 좋아요 ×3 + 저장 ×5, 초기값), 웹 서비스와 순위를 따로 집계한다.
- **반응:** 오픈소스에도 좋아요, 저장, 리뷰를 적용한다. 내용은 웹 서비스와 같다.
- **등록 항목:** 오픈소스는 기기 지원과 가격을 받지 않는다(해당 없음). 서비스 용도, 프로젝트 유형, 등록 주체, 태그는 웹 서비스와 같이 받는다. 지원 언어는 받지 않는다(제안).
- 웹 서비스에 붙은 코드 아이콘의 클릭은 집계하지 않는다.

구분: 확정(방식·반응 적용·기기와 가격 제외), 제안(지원 언어 제외)

### 4.11 팀원 소개·프로필 연결 (구현 우선순위 낮음)

- 고정 조직형 팀은 만들지 않고 서비스마다 공개 아이디로 회원을 검색해 초대한다. 수신자가 수락한 뒤 팀원이 된다. 등록자를 제외하고 서비스당 최대 5명이다.
- 수락한 팀원은 등록자와 같은 권한(서비스 관리·수정·삭제, 버전 기록 수정, 팀원 초대·삭제, 등록자 제거)을 가진다. 서로 아는 사람끼리 함께 운영하는 상황을 전제로 권한을 나누지 않으며, 팀원의 오남용은 감수한다. 역할 구분은 확장이다. 서비스 상세의 팀원, 팀원의 마이페이지·프로필의 본인 서비스로 연결한다. 기존 등록자 전용 관리·수정 규칙을 대체한다.
- 이전 서비스의 팀원 불러오기는 두지 않고 최근 검색한 아이디를 다시 고르는 흐름을 제공한다.
- 등록자가 탈퇴해도 팀원이 남은 서비스는 삭제하지 않는다. 탈퇴한 회원은 팀원 관계에서 빠지고 가장 먼저 수락한 팀원이 등록자 자리를 잇는다. 팀원이 없는 서비스는 기존대로 삭제한다.
- 팀원도 제작자로 취급한다. 자기 서비스의 좋아요·저장·단독 평가는 등록자와 똑같이 막고, 제작자 리뷰와 제작자 답글은 팀원도 쓸 수 있다.
- 초대 처리: 받은 사람이 거절하면 초대 알림을 지우지 않고 "거절함"으로 표시해 남기며(수락도 "수락함"으로 남긴다), 보낸 사람이 대기 중인 초대를 취소하면 초대와 받은 사람의 알림을 함께 삭제한다. 재초대는 제한하지 않고 대기 중인 초대의 중복만 막으며 팀원이 나간 뒤에도 다시 초대할 수 있다. 괴롭힘 초대는 따로 막지 않고 회원 신고로 처리한다. 보낸 사람에게는 수락·거절 결과를 알린다.
- 초대 만료·역할 표시는 확장이다.
- 구글 로그인·회원 기능·알림 이후 착수한다. 현재는 팀명만 입력하고 공유 권한·초대/수락 UI·업무 API는 미구현이다. 수락 초대만 연결하는 현행 DB 제약과 별개로 권한 적용을 구현해야 한다.
- 회원 고유 번호로 관계를 유지하고 수신자만 초대를 수락한다. 팀원 관리 권한을 비공개 이미지·대상의 무제한 공개로 해석하지 않으며 대상별 서버 권한을 검증한다. 팀원 서비스의 프로필 표시는 일반 서비스와 같은 공개 규칙을 따른다(타인에게는 공개 서비스만, 본인에게는 비공개 포함).

## 5. 탐색·노출

### 5.1 카드와 목록

- 카드형은 썸네일, 서비스 제목, 한 줄 소개, 좋아요 수, 저장 수를 표시한다. 목록형은 아이콘, 서비스 제목, 한 줄 소개, 좋아요 수, 저장 수를 표시한다. 제작자는 표시하지 않는다.
- 좋아요 수와 저장 수는 작은 아이콘과 숫자로 모바일을 포함해 항상 표시한다. 카드의 수치에는 별도의 반응 버튼을 붙이지 않는다.
- 사용자는 카드형·목록형을 고를 수 있다. 선택 전 모바일은 목록형, 데스크톱은 카드형이 기본이다. 두 선택지 전환은 선택된 쪽을 눌러도 다른 쪽으로 바뀐다.
- 가격은 등록자가 선택한 무료/유료/일부 유료를 사용한다. **데스크톱 카드의 가격 텍스트 배지는 이용하기처럼 마우스를 올렸을 때 표시**하고 상시 노출하지 않는다. 정확한 위치, 키보드 포커스 표시, 모바일·목록형 노출 방식은 미정 또는 제안이다. 상세의 이용하기 위에도 가격 유형과 짧은 설명을 표시하는 안은 제안이다. 무료 체험·일부 유료 구분 기준과 문구는 아직 확정하지 않았다.
- 데스크톱에서 카드·목록에 마우스를 올리면(또는 키보드로 포커스하면) 팝업이 아니라 카드 안에 평가 문구와 리뷰 수(예: "긍정적 (14)")와 `이용하기` 버튼이 나타난다. `이용하기`를 누르면 서비스 링크가 새 탭에서 열리고, 카드의 다른 부분을 누르면 상세 페이지로 이동한다. 운영 중지 서비스의 버튼은 비활성이다.
- 마우스를 올릴 수 없는 모바일에서는 카드의 `이용하기` 버튼을 생략하고(탭하면 상세로 이동), 평가 문구와 리뷰 수는 항상 표시한다.
- 서비스 상세에는 이름·소개·용도·제작자와 기기·가격·등록 주체·유형·언어, 이용하기·반응·통계를 표시한다. 제작자는 사진·닉네임으로 프로필에 연결하며 모든 서비스에 같은 웹 서비스 항목은 생략한다. 상세의 정확한 위치·표시 순서 변경은 이번 기능 동기화 범위에서 다루지 않는다.
- 상세의 서비스 소개는 마크다운으로 렌더링하고 기본은 접힌 상태(상단만 표시)로 둔다. 글이 길 때만 「더보기/접기」가 활성이고, 짧으면 비활성이다. 접는 기준(360자 또는 10줄 초과)은 제안이다.
- 상세 하단에 「비슷한 서비스」를 표시한다(기획서 3.2의 연계 노출 효과). 공개된 서비스만 쓴다. 구분: 제안(화면 표현)
- 서비스 상세 링크를 공유하면 서비스 이름, 한 줄 소개, 썸네일이 미리보기로 보이게 하고(OG 태그), 상세 페이지에 링크 복사 버튼을 둔다. Instagram 등 SNS로 홍보할 때 쓰기 위해서다.

### 5.2 홈

트렌딩·인기·최신 서비스를 요약해서 보여 준다. 관심 카테고리를 설정했다면 해당 카테고리의 트렌딩·인기를 우선 보여 준다. 섹션의 순서와 구성은 화면설계에서 정한다. (미정)

### 5.3 필터

프로젝트 유형, 기기 지원, 가격, 등록 주체, 지원 언어, 운영 상태로 필터링한다. 이용 형태 필터는 두지 않는다. **서비스 용도는 필터 패널이 아니라 목록 제목 아래 가운데의 카테고리 줄(전체 + 8개, 3·2·2·1개씩 구분선으로 묶음)**에서 고르며, 가장 자주 쓰는 필터이기 때문이다. 모바일로 접속하면 "모바일 지원 서비스만 보기" 토글이 켜진 상태로 시작하고, PC에서는 토글을 보여 주지 않는다. 서비스 용도 카테고리는 4.8을 따른다. 같은 그룹 안에서는 하나라도 해당하면 포함하고 서로 다른 그룹은 모두 만족해야 보인다(제안).

트렌딩·인기·최신은 같은 필터 상태를 공유하고 검색은 별도 상태를 쓴다. 용도 칩은 필터 패널 밖에 있으며 패널의 선택 개수에서 제외한다. “용도 제외 초기화”는 용도 선택을 유지하고 다른 필터만 초기화한다. 빈 결과의 전체 필터 초기화와 구분한다. 사이드바의 전체는 용도 선택을 해제한다. 구분: 확정

### 5.4 검색

아이디·닉네임으로 회원을 찾는 일반 회원 검색은 도입 방향으로 정했다. 서비스 검색과 팀원 초대용 아이디 검색을 구분하고, 중복 닉네임은 공개 아이디로 구별한다. 첫 출시 포함 여부, 검색 위치·일치 방식·정렬·결과 범위는 미정이며 구현 완료를 뜻하지 않는다(기획서 11.2).

| 항목 | 정책 | 구분 |
|---|---|---|
| 일반 검색 | 서비스 이름, 설명(한 줄 소개와 상세 설명), 태그에 검색어가 포함된 서비스를 찾는다 | 확정 |
| 정렬 | 관련도 / 인기 / 최신 | 확정 |
| AI 자연어 검색 | **MVP(후순위).** 화면 디자인에는 처음부터 반영하고, 구현은 일반 검색을 먼저 완료한 뒤 한다. 일정이 부족하면 확장으로 미룬다. 문장으로 입력하면 AI가 의도를 분석해 서비스를 찾는다 | 확정 |
| AI 검색 사용 제한 | 도입할 때는 호출 비용을 고려해 사용 횟수를 제한한다. 비회원은 하루 3회, 회원은 하루 20회(초기값). 횟수를 모두 쓰면 자연스럽게 일반 검색으로 전환한다 | 확정(방식), 제안(횟수) |
| 검색 결과 없음 | 안내 문구와 인기 서비스를 보여 준다 | 확정 |

### 5.5 트렌딩과 인기

| 항목 | 정책 | 구분 |
|---|---|---|
| 트렌딩 | 최근 3일 동안의 점수 합이 높은 서비스 | 확정 |
| 인기 | 사용자가 기간(주간/월간/전체)을 골라 누적 점수로 정렬 | 확정 |
| 점수 | 이용하기 클릭 ×1 + 좋아요 ×3 + 저장 ×5 (초기값, 데이터를 보고 조정). 리뷰와 조회수는 점수에 넣지 않는다. 오픈소스(확장)는 이용 집계 없이 좋아요와 저장만으로 따로 집계한다(4.10) | 확정(지표), 제안(가중치) |
| 순위 표시 | 트렌딩·인기 목록의 카드·목록에 순위 배지를 표시한다 | 제안(화면 표현) |
| 정렬 표시 | 트렌딩·인기·최신은 화면 고유 집계 기준을 정렬로 고정해 표시하고(인기만 기간 선택), 관련도·인기·최신 정렬 선택은 공개 탐색 중 검색 결과에만 둔다. 본인·저장 목록 정렬은 2.3의 별도 규칙을 따른다. 사이드바 용도 선택은 그 용도 하나를 선택한 트렌딩 목록으로 이동한다 | 제안 |

## 6. 반응과 리뷰

### 6.1 반응 종류

- 좋아요·저장: 회원이 서비스당 한 번 남기는 반응. 제작자 본인 서비스에는 불가하다.
- **서비스 평가:** 리뷰 글 없이 추천·비추천만 남길 수 있고, 이후 리뷰와 같은 평가 한 건을 공유한다.
- 리뷰: 의견 글과 평가 상태(추천 / 비추천 / 미설정). 서비스 평가 비율·등급에 반영한다.
- **리뷰 글 추천·비추천:** 다른 회원의 리뷰 글에 남기는 별도 반응. 서비스 평가·등급·인기 점수와 무관하다.
- 댓글: 리뷰와 별개인 이야기 공간. 평가·집계와 무관하다.

### 6.2 리뷰·서비스 평가 규칙

| 항목 | 규칙 | 구분 |
|---|---|---|
| 작성 조건 | 실제 외부 서비스 이용 여부는 검증하지 않는다 | 확정 |
| 회원 | 회원당 서비스 리뷰 1개. 글 없이 추천·비추천만 남길 수도 있다. 글을 추가하면 기존 평가와 합쳐 중복 집계하지 않는다 | 확정 |
| 단독 평가 변경 | 리뷰가 없을 때 같은 버튼을 다시 누르면 취소, 다른 버튼을 누르면 변경한다. 비회원·제작자 본인·운영 중지 서비스에는 허용하지 않는다 | 확정 |
| 리뷰 작성 후 평가 변경 | 버튼을 누르면 “리뷰를 수정할까요?”를 묻고, 동의하면 선택한 평가가 반영된 리뷰 수정 창을 연다. 저장 성공 후에만 바꾸고 취소하면 유지한다 | 확정 |
| 목록·숫자 | 글 없는 평가는 의견 목록에 올리지 않는다. 단독 평가를 리뷰 탭 숫자에 포함할지, 리뷰 삭제 후 평가를 유지할지는 미정이다 | 확정(목록 제외), 미정(숫자·삭제 후 처리) |
| 비회원 | 서비스가 허용한 경우 미설정 리뷰만 작성한다. 같은 IP로 서비스당 1개이며 수정은 불가하고 삭제는 관리자만 가능하다 | 확정 |
| 링크 | 리뷰·제작자 답글에는 링크를 넣을 수 없다 | 확정 |
| 익명 설정 | 등록자는 비회원 리뷰 허용·회원 익명 리뷰 허용을 따로 정하며 기본값은 둘 다 비허용이다. 익명 여부는 작성 시 정하고 수정 시 바꾸지 않는다 | 확정 |
| 수정 표시 | 수정한 리뷰·댓글·답글에는 날짜 옆에 `(수정됨)`을 표시한다 | 확정 |
| 주의 안내 | 익명 허용 시 스팸·비방·욕설 가능성을 등록자에게 안내한다 | 확정 |
| 제작자 본인·팀원 | 제작자 리뷰는 가능하나 평가 상태는 없고 등급·인기 점수에서 제외한다. 자기 서비스의 좋아요·저장·단독 평가는 불가하다. 팀원도 같은 제한을 받는다 | 확정 |
| 제작자 답글 | 등록자와 팀원만 다른 사람 리뷰에 답글을 달 수 있다. 리뷰당 1개를 제안하며 신고·관리자 삭제 대상이다 | 확정(권한), 제안(개수) |
| 리뷰 글 추천·비추천 | 다른 회원 리뷰에 남기며 본인 리뷰에는 불가하다. 서비스 평가·인기 점수에는 넣지 않는다. 회원당 리뷰 1표, 바꾸기·취소, 추천순(기본)·최신순은 제안 세부다. 추천순은 추천 수가 많은 순, 같으면 최신순을 제안한다 | 확정(별도 기능), 제안(세부) |
| 비회원 식별 | 전체 IP는 공개하지 않고 일부(IPv4 예 `123.45`)만 표시한다. 중복 방지는 전체 IP의 HMAC, 표시용 일부 IP는 별도 저장을 제안한다. IPv6 표시·키 관리·보관 기간·개인정보 요건은 미정이다 | 확정(일부 표시), 제안·미정(저장·운영) |

단독 평가·리뷰·목록은 현재 목업이며 실제 서버 저장·집계 연결이 필요하다. 리뷰 글 자체의 추천·비추천과 추천순·최신순 UI는 현재 프론트에 미구현이다. 익명 작성자의 내부 회원 ID는 공개 API에 보내지 않고 본인 여부·수정/삭제 가능 여부를 별도로 전달해야 한다.

### 6.3 평가 등급

추천 비율 = 추천 수 / (추천 수 + 비추천 수). 단독 평가와 리뷰의 평가를 같은 회원·서비스당 한 번만 세며 미설정·제작자 리뷰는 비율에서 제외한다.

| 조건 | 표시 | 구분 |
|---|---|---|
| 추천+비추천 5개 미만 | 평가 수 부족 | 확정 |
| 5~19개 | 긍정적(80% 이상) / 부정적(19% 이하) / 복합적 | 제안 |
| 20개 이상 | 80~100% 매우 긍정적, 70~79% 대체로 긍정적, 40~69% 복합적, 20~39% 대체로 부정적, 0~19% 매우 부정적 | 확정(비율 구간), 제안(20개 기준) |
| 많은 리뷰 구간 | 압도적으로 긍정적/부정적 등급은 두지 않거나 100개 이상 적용 | 미정 |

경계 비율의 반올림 처리 등은 구현 제안과 정책 확정을 구분한다. 서버 전체 집계를 반환할 때 현재 리뷰 목록을 다시 더하지 않는다.

| 탈퇴·서비스 삭제 | 다른 서비스에 쓴 댓글은 탈퇴한 사용자로 남기고, 서비스 삭제 시 해당 댓글·답글도 삭제한다(2.1·4.6) | 확정 |

좋아요·저장·리뷰 투표 수신 알림은 제외한다. 받은 반응 요약은 리포트 후보(M-66)에서 검토하며 리포트 도입을 확정한 것은 아니다. 신고자에게 처리 결과 안내·AI 검사 결과·주소 접속 불가 감지는 후속 확장이다. 현재 DB 3종·목업 5종과 확정 9종은 다르므로 API·스키마를 맞춰야 한다. DB 변경은 새 마이그레이션 파일로 추가하며 실제 SQL은 이번에 수정하지 않았다. 표현·보관·읽음/삭제의 세부는 미정이다.

| 항목 | 규칙 | 구분 |
|---|---|---|
| 방식 | 누적 알림창에서 다음 방문에도 조회할 수 있다. 현재 헤더 미읽음 최신 3건과 `/notifications` 목록은 목업이다 | 확정(누적), 현재 구현(화면) |

| 팀원 초대 | 수신자가 알림창에서 초대를 수락·거절한다. 처리한 알림은 지우지 않고 "수락함"·"거절함"으로 표시하며, 보낸 사람이 취소하면 초대와 알림을 함께 삭제한다. 수락하면 팀원으로 연결하고 보낸 사람에게 수락·거절 결과를 알린다. 현재 초대 UI·서버 연동은 미구현이다 | 확정(방향·처리), 후순위 |
| 알림 대상 | 위 9종과 팀 초대 별도 범위를 따른다. 자기 행동 알림 제외 등 구체적인 수신 조건·표현은 별도 확인한다 | 확정(종류), 미정(세부) |
| 수신자 | 본인 알림만 조회·처리한다. 초대 수락도 초대 수신자만 가능하다 | 권한 원칙 |
| 읽음·삭제·보관 | 목업은 전체/미읽음, 개별·전체 읽음/삭제를 제공한다. 실제 서버 저장·갱신·보관·삭제 대상 안내는 미정이다 | 현재 구현·제안·미정 |
| 실시간·푸시 | 엄격한 즉시 갱신과 브라우저·모바일 푸시는 요구하지 않는다. 이메일 알림도 확정 범위가 아니다 | 확정 |

## 7. 집계

| 항목 | 정책 | 구분 |
|---|---|---|
| 조회수 | 서비스 상세 페이지를 연 횟수. 화면에 표시만 하고 점수에는 넣지 않는다. 제작자 본인 조회는 제외 | 확정 |
| 실행 수 | `이용하기` 클릭 횟수. 상세 페이지와 카드·목록의 `이용하기` 클릭을 같은 실행 수로 집계한다. 모든 클릭을 집계한다. 제작자 본인 클릭은 제외. 코드 아이콘 클릭은 집계하지 않는다 | 확정 |
| 이상 징후 대응 | 같은 회원 또는 같은 IP(해시)가 같은 서비스를 1분 안에 10회 이상 또는 5분 안에 20회 이상 클릭하면, 그 서비스의 클릭을 1시간 동안 집계에서 제외한다(다른 서비스에는 영향 없음). 클릭 기록은 남기며, 기준은 데이터를 보고 조정한다 | 확정 |

## 8. 신고와 운영

| 항목 | 정책 | 구분 |
|---|---|---|
| 신고 주체 | 회원만 | 확정 |
| 신고 대상 | 서비스, 리뷰, 리뷰 답글, 댓글, 프로필(닉네임·소개) | 확정 |
| 신고 사유 | 서비스: 피싱·악성 / 부적절 콘텐츠 / 접속 불가 / 허위 정보 / 도용·소유권 / 기타. 리뷰·댓글: 스팸·광고 / 욕설·비방 / 개인정보 노출 / 기타. 프로필: 부적절한 표현 / 스팸·사칭 / 개인정보 노출 / 기타 | 확정 |
| 중복 신고 | 한 회원은 같은 대상을 한 번만 신고할 수 있다 | 확정 |
| 자동 임시 비공개 | 런칭 초반에는 서로 다른 회원 **4명 이상**이 신고하면 임시 비공개로 바꾸고 관리자에게 알린다. 서비스 규모가 커지면 기준을 올린다. 규칙 기반이며 AI는 쓰지 않는다. 프로필 신고로 숨겨지는 범위는 프로필(닉네임·소개)뿐이고 서비스·리뷰·댓글은 각자 신고로 처리한다. 사유별 임계값 차등은 두지 않는다. 탈퇴한 회원이 낸 신고도 집계에 포함하며, 자기 콘텐츠도 신고할 수 있고 같은 규칙으로 집계한다 | 확정(방식·수치·범위) |
| 관리자 처리 | 신고와 임시 비공개 건을 검토해 복구하거나 삭제한다. 서비스와 리뷰를 숨기거나 삭제하고 공개 상태를 바꿀 수 있다. 복구하면 그 대상의 열린 신고를 기각 처리하고 이후 새 신고만 다시 집계한다. 임시 비공개 중에도 등록자는 서비스를 수정할 수 있고 복구는 운영자가 판단한다(문의 이메일 접수) | 확정 |
| MVP의 관리자 기능 | **관리자 페이지를 MVP에 포함한다.** 최소 범위는 신고 목록·상세(대상 미리보기·사유·신고 건수), 처리(복구·최종 비공개·삭제·기각, 조치 이력 자동 기록), 임시 비공개 목록, 회원 제재 지정과 사유 알림, 조치 이력 조회이다. 관리자 권한은 개발자가 DB에서 직접 지정한 회원만 가지며 같은 구글 로그인으로 접근한다. 처리 대기 건수 확인이 관리자 알림 방식이다. 통계 대시보드·공지·일괄 처리는 확장이다 | 확정 |
| 비공개·삭제 통지 | 관리·마이페이지의 상태/사유와 위 6.5의 임시 비공개·해제·최종 비공개·작성 대상 제한·등록 제한 알림 종류를 따른다. 표현·보관은 미정이다 | 확정(종류·상태), 미정(세부) |
| 이의 제기 | 문의 이메일(tndus10@skuniv.ac.kr, 임시)로 안내한다 | 확정 |
| 신고자 | 신고자는 작성자에게 공개하지 않는다. 허위 신고 대응은 MVP에 두지 않는다. 신고자에게 처리 결과를 알리는 것은 확장이다. 단시간 대량 신고 제한은 구현 때 정한다 | 확정 |
| 악성 서비스 대응 | 운영진 사전 승인 없이 즉시 등록·공개하고, 등록 후 URL 평판 조회와 등록 글·이미지의 AI 유해성 검사를 진행하는 방향이다. 신고·관리자 숨김·삭제도 유지한다. 외부 사이트의 실제 브라우저 실행·화면·동작 검사는 이번 채택 범위에 포함하지 않는다. 접속 검사 방식, 검사 제공자·모델·시점·실패·재시도·자동 임시 비공개·운영자 확인 기준은 미정이다. 신고 인원 기준의 자동 임시 비공개와는 별도 절차다 | 확정(방향), 미정(세부) |

## 14. 용어

- **서비스:** 개발자가 만든 웹 서비스. WEBTER에 등록되는 대상
- **이용하기:** 서비스 링크(실행 주소)를 새 탭에서 여는 버튼
- **오픈소스:** GitHub 링크만 있고 서비스 링크가 없는 서비스(확장)
- **이용 형태:** 웹 서비스 / 오픈소스(확장) / (확장) 사이트 안에서 이용. 입력한 링크로 정해진다
- **리뷰:** 서비스에 남기는 의견 글과 평가 상태(추천/비추천/미설정)
- **서비스 평가:** 글 없이 또는 리뷰와 함께 남기는 추천·비추천. 회원·서비스당 한 건만 집계
- **리뷰 글 추천·비추천:** 다른 회원 리뷰 글의 별도 반응. 서비스 평가 집계에는 미포함
- **반응:** 서비스 평가·리뷰·좋아요·저장(리뷰 글 추천/비추천은 별도)
- **댓글:** 리뷰와 별개로 상세에서 나누는 이야기. 평가·집계와 무관
- **등록자:** 서비스를 등록한 회원
- **운영 상태:** 서비스를 지금 쓸 수 있는지 나타내는 상태(운영 중/운영 중지)
- **공개 상태:** 서비스가 목록에 노출되는지 나타내는 상태(공개/비공개, 임시 비공개 포함). 공개일 때는 화면에 표시하지 않는다

## 16. MVP 개발 우선순위

실제 런칭을 위한 첫 출시 기능의 **개발 순서 제안**이다. 1단계 완료만으로 첫 출시 범위 전체를 완료한 것으로 보지 않는다. 기능 범위를 이 문서 최신화에서 임의로 줄이지 않으며, 범위 변경은 사용자가 결정한다. AI 자연어 검색은 일반 검색 이후 구현하고 일정 부족 시 확장으로 둘 수 있다는 기존 정책을 유지한다(10). 단계 배치는 개발하면서 조정한다.

| 단계 | 기능 | 의미 |
|---|---|---|
| 1단계 (핵심 흐름) | 구글 소셜 로그인과 온보딩(약관 동의, 아이디·닉네임), 로그인 안내와 원래 페이지로 복귀, 서비스 등록(서비스 링크, 분류, 등록 시 확인 체크, 주소 검증), 홈(최신·인기 기본), 목록·카테고리·기본 필터, 일반 검색, 서비스 상세와 `이용하기`, 조회수·`이용하기` 클릭 기록(저장만), 좋아요·저장, 리뷰(추천/비추천/미설정), 제작자 프로필(기본 정보·외부 링크·서비스 목록), 마이페이지(내 서비스·저장·리뷰·댓글·설정), 기본 반응형, 링크 공유 미리보기(OG)와 링크 복사, 약관·개인정보처리방침 페이지(임시) | 핵심 사용자 흐름을 먼저 연결하는 개발 단계 |
| 2단계 (완성도) | 평가 등급 표시(카드·목록·상세), 제작자 답글, 댓글, 리뷰 추천/비추천과 정렬(제안), 비회원 리뷰와 익명 설정(IP 해시), 관심 카테고리와 홈 우선 표시, 트렌딩, 카드·목록 보기 전환, 모바일 지원 필터 토글, 버전 기록, 신고(서비스·리뷰·답글·프로필)와 자동 임시 비공개, 관리자 페이지, 운영 상태(운영 중/운영 중지) | 첫 출시 범위의 반응·운영·탐색 기능 |
| 3단계 (후속 구현) | AI 자연어 검색, GitHub 링크 입력과 코드 아이콘, 이상 징후 집계 제한, 인기 기간 선택, 마크다운 소개, 미리보기 이미지 최대 8장과 맞춤 방식(꽉 채우기 편집), 지원 언어 필터, 하루 등록 개수 제한 | 후속 구현 단계(AI 검색의 범위 조정은 10장 기준) |

등록 후 URL 평판·등록 글/이미지 유해성 검사와 비공개 이미지 새 요청 제한은 방향이 확정됐으나 세부 구현이 미정이다. 단계 배치는 아직 정하지 않았으며 별도 운영 설계가 필요하다. 카드 가격 hover 표시는 탐색 화면 구현에 반영한다. 누적 알림창의 구현 순서는 미정이고, 팀원 초대·참여 프로젝트는 낮은 우선순위로 관리한다(4.11·6.5·11).

특히 무거운 항목은 비회원 리뷰(IP 식별과 익명 설정), 이미지 맞춤 편집, 신고 자동 처리와 위 운영 검사·이미지 접근 제한이다.

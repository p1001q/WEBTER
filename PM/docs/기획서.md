## 1. 프로젝트 개요

| 항목 | 내용 |
|---|---|
| 프로젝트명 | WEBTER (웹터) |
| 이름의 의미 | Web + 터. 웹 서비스를 모아 놓은 터. 장터, 놀이터처럼 여러 의미로 확장되는 한국어 이름 |
| 슬로건 | 웹이 모이는 터, 웹터 |
| 보조 문구 | 찾던 웹도, 몰랐던 웹도 웹터에서 만나보세요 |
| 한 줄 소개 | 개발자가 만든 웹 서비스를 한곳에서 발견하고, 설치 없이 바로 이용하며, 리뷰·좋아요·저장으로 반응을 남기는 웹 서비스 스토어 |
| 형태 | 데스크톱과 모바일을 고려한 반응형 웹 (PWA는 확장 기능) |
| 개발 기간 | 2026년 10월 초 ~ 11월 25일(첫 출시 범위 구현 목표). 발표 일정은 1차 11/27, 2차 12/04, 최종 12/09 |
| 팀 | 얼렁뚱땅 (박수연, 박성영) |

이 문서의 **MVP는 실제 런칭을 목표로 하는 첫 출시 범위**를 뜻한다. 발표용 시연만을 목표로 하지 않으며, 문서 최신화로 기능 범위를 임의로 축소하지 않는다. 주요 화면 퍼블리싱을 구현했고 기능별 API 구현·연동을 진행하며 세부 기능을 다듬는다.

### 핵심 기능

- 서비스 탐색: 홈, 트렌딩·인기·최신, 카테고리, 필터, 검색, 관심 카테고리, 카드형·목록형 보기
- 외부 웹 서비스 실행: `이용하기` 버튼으로 새 탭에서 실행, 소스를 공개한 서비스는 코드 아이콘(`</>`)으로 연결
- 서비스 등록 및 관리: 서비스 링크(선택적으로 GitHub 링크)를 등록, 운영 상태 관리, 버전 기록
- 회원 반응: 서비스 단독 평가·리뷰(추천/비추천/미설정)와 리뷰 글 추천/비추천, 댓글, 좋아요, 저장. 스팀 방식의 평가 등급 표시
- 소셜 로그인 기반의 단일 회원 체계: 이용자와 개발자를 구분하지 않음
- AI 활용: 자연어 검색으로 서비스 탐색을 돕는 기능 (MVP 후순위, 일반 검색을 먼저 완료한 뒤 구현)

### 현재 개발 상태와 기술 구성

- **현재 단계:** 주요 화면의 1차 퍼블리싱과 목업 상호작용을 구현했고, 백엔드 업무 API 구현과 프론트 연동을 기능별로 함께 진행하는 단계다. 미구현 요구사항과 화면별 세부 조정은 남아 있으며, 전체 반응형·접근성·실제 서버 연동의 완료를 뜻하지 않는다.
- **개발 순서:** 기능별 백엔드 API 구현과 프론트 연결을 함께 진행하고 저장 유지·권한·실패 처리를 확인한 뒤, 구현·연동 결과에서 ERD와 API 명세서를 정리한다. 기존 ERD는 참고 검토본이며 데이터 관계·중복 제약·요청/응답은 해당 기능을 개발하기 전에 맞춘다.
- **확정 기술:** 프론트는 Next.js(App Router)·React·TypeScript·Tailwind CSS, 주 글꼴은 Pretendard다. 복잡한 스타일만 CSS Modules로 분리한다. 백엔드는 Spring Boot(Java 21), DB는 PostgreSQL이다. 세부 버전과 실행 방법은 `FE/README.md`·`BE/README.md` 및 각 설정 파일을 따른다.
- **ERD:** 현행 검토본과 과거 비교 자료를 `other/DB설계/README.md`에서 구분한다. 현행은 Supabase 외부 회원 FK를 사용하지 않으며, 물리 테이블·컬럼은 검토용 구현 설계 제안이다. 설계 갱신을 운영 DB 적용이나 인증·업무 권한 구현 완료로 보지 않는다.
- **현재 구현:** BE 엔티티·리포지토리·Flyway V1~V4·기본 데이터·공통 응답/예외·CORS·OpenAPI·Testcontainers 기반이 준비돼 있다. 로컬은 Flyway와 JPA validate, 운영은 자동 DDL·앱 실행 시 마이그레이션 비활성화다. 구글 OIDC·서버 세션·가입·계정 설정·로그아웃·탈퇴는 구현해 `develop`에 반영했다. 서비스·평가·리뷰·댓글·알림·좋아요·저장 등 업무 데이터 연동 완료와 구분한다.
- **운영:** AWS와 단일 EC2의 앱·PostgreSQL·Redis Docker Compose 구성을 기준으로 Terraform·GitHub Actions 배포 초안을 작성했다. 서버 제공 방식·관리 범위 확인 전까지 실제 서버 생성·결제·배포 세팅은 보류한다. Supabase DB/Auth 사용 전제는 철회했다. 개발·시연 단계는 프론트 Vercel Hobby와 백엔드 EC2 서브도메인 구조로 진행하고 운영 도메인은 구매한다. 런칭이 확정되면 Vercel 요금제와 서버 사양을 다시 정한다.
- **퍼블리싱:** 홈·목록·검색·상세·등록/수정·관리·프로필·마이페이지·알림·로그인·온보딩·약관 화면과 오류·빈 상태를 구현했다. 실제 업무 데이터는 목업이며 개발 도구는 프로덕션에서 제외한다. 구글 OIDC·서버 세션·가입·계정 설정·로그아웃·탈퇴는 구현해 `develop`에 반영했다. 서비스·평가·리뷰·댓글·알림·좋아요·저장 등 업무 데이터 연동 완료와 구분한다.

## 2. 배경과 문제

### 2.1 배경

- AI 개발 도구와 바이브 코딩이 확산되면서 개인이나 소규모 팀도 웹 서비스를 빠르게 만들고 배포할 수 있게 되었다.
- 그러나 서비스를 만든 뒤 사용자를 모으고 반응을 확인하는 과정은 여전히 여러 채널로 나뉜다.

### 2.2 사용자가 겪는 문제

- 흥미로운 웹 서비스를 SNS 알고리즘 추천으로만 접하게 된다. 원하는 서비스를 능동적으로 찾을 경로가 없다.
- 서비스를 소개하는 홍보 계정을 따라가거나, 게시물을 타고 들어가 링크를 받아야 한다.
- 서비스에 대한 반응이 댓글에 흩어져 있어 확인이 번거롭고, 결국 보지 않게 된다.
- SNS는 주로 모바일에서 쓰는데 웹 서비스는 PC에서 쓰고 싶은 경우가 많아, 모바일에서 웹으로 옮겨 가는 과정이 불편하다.

### 2.3 아이디어 발전 과정

| 단계 | 관찰과 판단 |
|---|---|
| 1 | 바이브 코딩으로 웹 서비스 제작 접근성이 높아졌다 |
| 2 | Instagram 게시물과 자동 DM 등으로 서비스를 홍보하고 링크를 전달한다 |
| 3 | 홍보, 서비스 정보, 반응이 SNS 안에서 뒤섞이거나 여러 채널로 분산된다 |
| 4 | SNS는 홍보와 유입을 맡고, 별도 플랫폼이 등록·탐색·피드백을 맡는 구조를 구상했다 |
| 5 | 디스콰이엇 등 유사 서비스의 운영 사례를 확인하고 웹 서비스 스토어 관점에서 발전 가능성을 검토했다 |

### 2.4 해결하려는 문제와 해결 방향

| 문제 | 현재 상황 | 해결 방향 |
|---|---|---|
| 발견 | 독립 웹 서비스가 SNS·커뮤니티에 흩어져 있어 찾기 어렵다 | 카드형·목록형 보기, 상세 페이지, 정렬별 탐색 |
| 이용 연결 | 홍보 게시물에서 실제 서비스까지 이동 경로가 일정하지 않다 | 상세 페이지의 `이용하기` 버튼으로 외부 서비스에 바로 연결 |
| 운영 | 제작자가 소개·링크·운영 상태를 여러 채널에서 관리한다 | 등록, 수정, 상태 관리를 한 화면에 모음 |
| 피드백 | 댓글·DM·설문에 반응이 분산된다 | 서비스 상세 페이지에 리뷰 공간을 둠 |

### 2.5 검증 상태

- 사용자 쪽 문제는 작성자의 직접 경험에서 나왔고, 제작자 쪽 문제(운영·피드백 분산)는 작성자의 추정이다. 둘 다 별도의 수요 조사로 검증하지 않았다.
- 유사 서비스(디스콰이엇 등)의 운영은 이런 서비스의 수요 가능성을 보여주지만, WEBTER의 수요가 검증되었다는 의미는 아니다.

## 3. 해결 방식과 핵심 가치

### 3.1 해결 방식

WEBTER는 웹 서비스를 한곳에 모아 보여 주고, 설치 없이 바로 이용하도록 연결하는 웹 서비스 스토어다. 지금 바로 이용할 수 있는 서비스만 모은다.

- **모으기:** 제작자가 배포한 웹 서비스의 링크(선택적으로 GitHub 링크)를 등록하고 관리한다
- **찾기:** 홈(트렌딩·인기·최신), 카테고리, 검색으로 탐색한다. 검색어를 정확히 모르면 목적을 문장으로 입력하는 AI 자연어 검색을 쓴다(MVP 후순위)
- **이용하기:** 상세 페이지나 카드(데스크톱 hover)에서 `이용하기`를 누르면 외부 서비스가 새 탭에서 열린다
- **반응 남기기:** 회원은 리뷰(추천/비추천/미설정), 좋아요, 저장으로 반응을 남기고 다른 회원의 리뷰에 추천/비추천을 남길 수 있다. 등록자가 허용한 서비스에는 비회원도 리뷰를 남길 수 있다. 리뷰와 별개로 댓글로 서비스에 대해 이야기를 나눌 수 있다

### 3.2 SNS와의 관계

일반 사용자는 Instagram, YouTube 같은 SNS를 압도적으로 자주 사용하므로, 마케팅과 유입은 SNS가 맡는 구조가 자연스럽다. WEBTER는 SNS를 대체하지 않고, 유입된 사용자가 서비스를 실행하고 상태를 확인하고 반응을 남기는 곳을 맡는다.

| 영역 | 담당 역할 | 사용자 흐름 |
|---|---|---|
| SNS | 홍보와 관심 유도 | 홍보 게시물에서 WEBTER 상세 페이지로 이동 |
| WEBTER | 서비스 등록, 실행 연결, 상태 관리, 반응 관리 | 서비스를 비교하고 정보를 확인한 뒤 이용 여부 결정 |
| 외부 웹사이트 | 실제 서비스 실행 | `이용하기`로 새 탭에서 사용 |

**진입 과정 개선:** 인스타 홍보에서 댓글 작성 → 팔로우 확인 → DM 링크 전송을 기다리거나, 게시글 주소를 바로 열기 어려워 캡처 후 인식하거나, 프로필 링크에서 해당 서비스를 다시 찾는 과정이 생긴다. 관심이 생긴 사용자가 이런 단계를 덜 거쳐 WEBTER 안의 해당 서비스 상세로 진입하고 `이용하기`에 쉽게 접근하게 하는 것이 목표다. 링크 복사·QR·홍보 이미지 등 수단의 선택과 도입 시점은 11.4에서 검토한다. 웹터가 인스타의 링크·캡처 동작을 제어할 수 있다고 전제하지 않는다.

**연계 노출 효과(가설):** 한 서비스에 관심을 가져 들어온 사용자가 목록, 카테고리, 다른 서비스 카드를 통해 다른 서비스도 발견하고 이용하도록 한다. 제작자에게 실제 사용자 한 명 한 명의 유입과 반응이 중요하다는 점을 핵심 가치로 본다. 다른 서비스의 발견·이용 증가는 기대효과이며 검증된 성과는 아니다.

### 3.3 핵심 가치

- **발견:** 흩어진 웹 서비스를 한곳에서 탐색한다
- **접근 편의:** 서비스를 찾고 실행 링크에 접근하는 단계를 줄이며, 별도 설치 없이 외부 웹 서비스를 이용한다
- **등록과 홍보:** 제작자가 서비스를 등록하고 사용자에게 노출한다
- **반응:** 사용자는 반응을 남기고, 제작자는 서비스별 반응을 확인한다
- **서비스 중심:** 개발자 개인보다 개발자가 만든 서비스를 중심으로 보여 준다

### 3.4 동작 원칙

- MVP에서는 서비스 링크를 등록받아 새 탭에서 열며(소스를 공개한 서비스는 GitHub 링크도 받아 아이콘으로만 연결), 직접 호스팅하거나 iframe으로 실행하지 않는다(사이트 안에서 바로 실행하는 내부 연결은 확장 1순위, 부록 A). 이유는 다음과 같다.
  - 외부 서비스의 보안 정책으로 iframe 실행이 제한될 수 있다
  - 외부 서비스의 로그인, 결제, 개인정보 처리 책임을 WEBTER와 분리할 수 있다
  - 구현 범위를 줄이고 다양한 웹 서비스를 연결할 수 있다
- 카드 본문을 누르면 상세 페이지로 이동하고, `이용하기`(데스크톱에서 카드에 마우스를 올리면 나타남)를 누르면 외부 사이트를 연다. 카드의 `이용하기` 클릭도 상세 페이지와 같은 실행 수로 집계한다
- 소스 코드 관리나 종합 프로젝트 관리 기능은 범위에서 제외한다
- 배포 전 서비스는 받지 않는다. 사용자가 바로 이용할 수 있는 서비스만 모은다
- WEBTER가 측정할 수 있는 행동은 `이용하기` 클릭과 서비스 상세 조회까지다

## 4. 서비스 분류와 탐색 구조

### 4.1 분류 기준

서비스는 아래 표의 다섯 가지 기준과 이용 형태, 지원 언어로 분류한다. 이용 형태는 등록자가 입력한 링크에 따라 정해지고, 나머지는 등록자가 직접 선택한다.

- 이용 형태: 웹 서비스 / 오픈소스(확장, GitHub 링크만 있는 서비스). 내부 연결(사이트 안에서 이용)은 확장이다. 웹 서비스에 GitHub 링크를 함께 입력하면 소스 공개 서비스로 코드 아이콘이 표시된다.
- 지원 언어: 한국어 / 영어(복수 선택, 기본값은 한국어)

| 기준 | 값 | 비고 |
|---|---|---|
| 서비스 용도 | 놀이, 일상, 학습, 업무, 창작, 간편 도구, 개발 도구, 기타 | 복수 선택 가능. 소분류는 태그가 대신한다 |
| 프로젝트 유형 | 토이 프로젝트 / 사이드 프로젝트 / 정식 서비스 | 만든 목적과 운영 계획으로 구분 |
| 기기 지원 | PC / 모바일 (복수 선택) | 모바일은 반응형, 웹앱 등 모바일에서 불편 없이 쓸 수 있으면 해당 |
| 가격 | 무료 / 유료 / 일부 유료 | |
| 등록 주체 | 개인 / 팀 | 팀이면 팀명을 입력 |

### 4.2 프로젝트 유형 정의

| 유형 | 만든 목적 | 운영 계획 |
|---|---|---|
| 토이 프로젝트 | 학습, 재미, 실험 | 지속 운영 계획 없음 |
| 사이드 프로젝트 | 사용자에게 제공할 의도가 있음 | 운영을 이어갈 계획이 있음 |
| 정식 서비스 | 본업이나 창업으로 운영하는 서비스(팀·회사 포함) | 지속 운영 |

### 4.3 탐색 방식

- 가격 텍스트 배지는 데스크톱 카드에 마우스를 올렸을 때 표시한다. 모바일·목록형·정확한 위치·상세 CTA 표시 문구와 무료 체험 구분 기준은 미정 또는 제안이다(정책서 5.1).
- 사용자는 서비스 용도, 프로젝트 유형, 기기 지원, 가격, 등록 주체, 지원 언어, 운영 상태를 선택해 서비스를 골라 볼 수 있다. 예를 들어 놀이, 팀, 모바일 지원 서비스만 모아 볼 수 있다. 가장 자주 쓰는 서비스 용도는 필터 패널이 아니라 목록 위 가운데의 카테고리 줄에서 고르고, 이용 형태는 지금 고를 수 있는 값이 없어 필터로 두지 않는다.
- 서비스는 카드형과 목록형 중 하나를 고른다. 선택 전 모바일은 목록형, 데스크톱은 카드형이 기본이다. 카드형은 썸네일, 서비스 제목, 한 줄 소개, 좋아요 수, 저장 수를 보여 주고, 목록형은 아이콘, 서비스 제목, 한 줄 소개, 좋아요 수, 저장 수를 보여 준다(수치는 모바일에서도 항상 표시). 데스크톱에서 마우스를 올리면 카드 안에 평가 문구와 리뷰 수, `이용하기` 버튼이 나타나고, 모바일에서는 이용하기 버튼을 생략하고 평가 문구를 항상 표시한다.
- 모바일로 접속하면 모바일에서 바로 즐길 수 있는 서비스가 먼저 보이도록 "모바일 지원 서비스만 보기" 토글이 켜진 상태로 시작한다.
- 토글을 끄면 PC 전용 서비스도 볼 수 있다. 모바일에서 PC 전용 서비스를 발견하면 저장해 두었다가 PC에서 이용할 수 있다.
- PC로 접속하면 토글을 보여 주지 않고, 기기 지원을 포함한 필터와 검색으로 탐색한다.
- 사용자가 관심 카테고리를 설정하면 홈에서 해당 카테고리의 트렌딩·인기 서비스를 우선 보여 준다.
- 서비스 용도는 복수로 선택할 수 있고, 세부 분류는 태그가 맡는다. 등록할 때 이름과 설명을 보고 태그를 추천해 주는 기능은 확장이다.
- 서비스에는 등록자가 바꿀 수 있는 운영 상태(운영 중/운영 중지)가 있다. 운영 중지 상태이면 사유를 한 줄로 적어 서비스 상단에 보여 주고, 기본 목록에서는 숨긴다. 필터에서 선택하면 볼 수 있고, 필터의 기본값은 "운영 중"이다. 운영 중지 서비스에도 좋아요·저장은 가능하고, 리뷰는 추천·비추천 없이 쓸 수 있다.
- WEBTER는 기본 반응형 웹으로 개발해 모바일 접속에서도 화면이 깨지지 않게 한다.

### 4.4 서비스 이미지

1차 연동에서 이미지 업로드를 S3로 구현한다(M-77). 비공개 버킷에 CloudFront를 앞에 두고 브라우저가 일회용 주소로 직접 올리며, 백업용 버킷과 분리한다. 장당 5MB를 넘는 이미지는 올리기 전에 브라우저에서 자동 압축하고(아이콘은 적극적으로, 서비스 화면은 약하게) 서버는 형식·용량을 다시 검증한다(M-81). 아래는 이미지 종류·표시 기준이다.

한 서비스에는 세 종류의 이미지가 쓰이며, 모두 선택 입력이다.

| 이미지 | 용도 | 규칙 |
|---|---|---|
| 아이콘 | 목록형 보기 | 정사각형 |
| 썸네일 | 카드형 보기 | 카드 비율로 잘라서 등록 |
| 미리보기 | 상세 페이지 | 최대 8장. 서비스마다 가로 16:9 또는 세로 9:16 중 하나로 통일. 이미지 맞춤은 "꽉 채우기"(가운데 기준 자동 맞춤)와 "전체 보이기" 중 선택. 직접 크롭·위치 조정 도입은 미정 |

아이콘과 썸네일을 올리지 않으면 선택한 서비스 용도별 기본 이미지를 보여 주고, 미리보기를 올리지 않으면 해당 영역은 생략한다.

### 4.5 추가 계획·확장 후보

- 서비스별 팀원 초대를 제공한다. 등록자 제외 최대 5명, 수락 후 등록자와 같은 권한(관리·수정·삭제, 버전, 팀원 초대/삭제, 등록자 제거)을 가지며 본인 서비스로 연결한다. 로그인·회원·알림 이후 착수한다. 등록자가 탈퇴해도 팀원이 남은 서비스는 유지하고 먼저 수락한 팀원이 등록자 자리를 잇는다. 팀원도 제작자로 보아 자기 서비스 좋아요·저장·리뷰 평가는 등록자와 같이 막고 제작자 답글은 팀원도 쓴다. 고정 조직·이전 팀원 불러오기는 두지 않으며 초대할 때 최근 검색한 아이디를 다시 고를 수 있다.
- 위 팀원 기본 기능 이후의 고도화와 PWA·제작 이야기·공개 전환·오픈소스 등 확장 목록은 11장에서 함께 관리한다. 현재의 한 단계 서비스 용도와 태그 구조는 유지하며 하위 카테고리는 확장 검토 항목이다.

## 5. 대상 사용자

### 5.1 주 타깃

일반 사용자와 제작자가 모두 주요 사용자이며, 서비스를 이용하는 일반 사용자를 먼저 고려한다.

이 서비스의 출발점은 SNS(Instagram)에서 서비스를 소개받아도 실제 이용으로 이어지기 어렵다는 경험이다. SNS는 주로 모바일에서 서비스를 둘러보는 용도로 쓰이고, 실제로 이용하려면 링크를 찾고 웹으로 이동하는 등 몇 단계를 거쳐야 한다. 단계가 적더라도 번거로우면 이용까지 가지 않는다. WEBTER는 발견에서 이용까지의 단계를 줄이는 데 초점을 둔다.

### 5.2 사용자 구분

| 구분 | 대상 |
|---|---|
| 서비스를 이용하는 사용자 | 새로운 웹 서비스를 발견하고 싶은 일반 사용자, 웹게임·인터랙티브 콘텐츠를 찾는 사용자, 문제를 해결할 웹 도구를 찾는 사용자, 다른 개발자의 서비스를 체험하려는 개발자 |
| 서비스를 등록하는 사용자 | 누구나 서비스를 등록할 수 있다. 독립 개발자, 학생, 초보 개발자, 사이드 프로젝트 개발자, 바이브 코딩으로 만든 제작자, 소규모 팀 등. 숙련도나 제작 방식으로 등록을 제한하지 않는다 |

### 5.3 회원 구조

회원가입 시 일반 사용자와 개발자를 구분하지 않는 단일 회원 체계를 쓴다. 한 사람이 이용자와 제작자 역할을 오갈 수 있다는 실제 사용 방식을 반영한 결정이다. 첫 출시에서는 구글 소셜 로그인만 제공한다. 구글 인증과 WEBTER 가입 완료를 구분하고, 미가입자는 온보딩 최종 제출에서 가입을 완료한다. 중도 이탈한 입력·진행 단계는 저장하지 않으며 다음 로그인 때 처음부터 진행한다. 카카오·네이버·GitHub 등 추가 공급자의 도입 시점과 계정 연결·분리 정책은 미정이다. 현재 로컬 인증 구현은 구글 OIDC와 백엔드 서버 세션을 사용하며 운영 세션 유지·재인증·여러 기기·도메인 구성은 별도로 정한다. 계정에는 중복 불가이며 변경할 수 있는 아이디(공개 식별자)와 중복이 가능한 닉네임을 설정한다. 닉네임은 최소 1글자, 한글 2칸·영문/숫자/공백 1칸을 합해 최대 16칸이며 혼용을 허용한다. 중간 단일 공백만 허용하고 초성·모음·특수문자·이모지는 금지한다. 부적절한 닉네임은 금지하되 자동 욕설 필터는 두지 않는다(정책서 2.1). 이 규칙은 FE·BE 검증에 적용했다.

가입은 별도 화면 없이 사용 흐름 안에서 이루어진다. 비회원으로 둘러보다가 회원 기능(리뷰 평가, 좋아요, 저장, 서비스 등록, 신고 등)을 누르면 로그인 안내가 나오고 로그인 화면으로 이동한다. 구글 인증 후 기존 회원은 보던 페이지로 돌아가고, 미가입자는 온보딩(약관 동의, 아이디·닉네임 설정, 관심 카테고리 선택은 건너뛰기 가능)의 최종 제출로 가입을 완료한 뒤 보던 페이지로 돌아간다.

현재 구글 로그인·온보딩 최종 가입·세션 복원·계정 설정·로그아웃·회원 탈퇴와 프론트 연결은 로컬 작업에서 구현했다. 가입 도중 약관 버전이 바뀌면 최신 버전을 조회하고 동의를 해제해 약관 단계에서 다시 확인받는다. 현재 화면의 입력은 유지하지만 이탈 후 복원은 하지 않는다. 서비스·리뷰·댓글·알림·좋아요·저장 등은 목업이며 실제 업무 API 연동과 구분한다.

| 사용 상태 | 가능한 행동 |
|---|---|
| 비회원 | 목록·상세 조회, 검색, 카테고리 탐색, 외부 서비스 실행, 등록자가 비회원 리뷰를 허용한 서비스에 평가 상태 없는 리뷰 작성 |
| 회원 | 비회원 기능 + 모든 서비스에 리뷰(추천/비추천/미설정), 리뷰 추천/비추천, 댓글, 좋아요, 저장 |
| 서비스 등록 회원 | 회원 기능 + 서비스 등록·수정·삭제 및 운영 상태 관리 |

### 5.4 제작자 프로필과 외부 연결

- 서비스 상세 페이지에는 제작자의 프로필 사진과 이름이 표시되고, 누르면 제작자 프로필로 이동한다. 카드에는 제작자를 표시하지 않는다.
- 제작자 프로필에는 프로필 사진, 닉네임, 아이디, 한 줄 소개, 블로그·GitHub·Instagram·Velog·포트폴리오 등 외부 링크, 등록한 서비스 개수, 받은 좋아요 수, 등록한 서비스 목록이 표시된다. 외부 링크 연결은 MVP에 포함한다. 팔로워 수는 표시하지 않고, 활동 레벨은 확장 기능이다.
- 제작 회고나 글을 쓰는 기능은 WEBTER에 만들지 않는다. 이미 회고를 쓸 수 있는 서비스가 많고, 회고를 궁금해하는 사람은 해당 서비스나 제작자에 관심이 큰 소수(주로 개발자)이기 때문이다. 이런 사용자는 외부 링크로 연결하면 충분하다. 다만 정해진 형식의 짧은 "제작 이야기"와 회고 외부 링크 연결은 확장 기능으로 검토한다.
- 플랫폼 안에 글 기능을 두면 서비스를 이용하려는 일반 사용자에게는 읽을 거리가 늘어 부담이 될 수 있다. WEBTER는 글이 아니라 서비스를 중심으로 연결된다.

알림은 사이트 내 알림창에서 누적 내역을 확인하고 답글 위치로 이동하는 방식이다. 팀원 초대 수락도 알림창에서 처리한다. 엄격한 실시간 갱신과 브라우저·모바일 푸시는 요구하지 않는다. 알림 종류는 9종으로 확정했고 팀 초대는 별도다. 수신 조건·표현·읽음·보관·구현 순서는 미정 또는 제안이다(정책서 6.5).

서비스별 초대를 수락하면 팀원 본인 마이페이지·프로필에도 본인 서비스로 연결하고 등록자와 같은 권한(서비스 삭제·등록자 제거 포함)을 가진다. 등록자 제외 최대 5명이며 팀원이 남은 서비스는 등록자가 탈퇴해도 유지한다. 팀원별 외부 링크를 각 회원 프로필에서 관리하는 방식과 Notion 등 링크 종류는 검토 사항이다.

### 5.5 향후 확장 방향

공개 프로필 확장·활동 레벨·팔로우와 피드 등 기존 확장 기능과 아이디·닉네임 회원 검색, 팀 고도화의 도입 상태는 11장에서 관리한다. 현재 제작자 프로필과 서비스별 팀원 기본 기능은 위 5.4와 정책서의 현행 범위를 따른다.

### 6.2 차별점

핵심 차별점은 다음 순서로 둔다.

1. **서비스 중심 구조:** 글, 회고, 커뮤니티 기능을 두지 않고 서비스 목록과 이용에 집중한다. 제작자 이야기는 프로필의 외부 링크로 연결한다.
2. **빠른 서비스 이용:** 상세 페이지의 `이용하기` 한 번으로 서비스가 열린다.
3. **웹 전용:** 설치형 앱이 아니라 웹 서비스만 대상으로 한다.

한모아와 비교하면 위 세 가지는 겹치는 부분이 있다. 그래서 다음 요소가 차이를 만든다.

- **로그인 없이 리뷰:** 서비스 등록자가 서비스마다 비회원 리뷰 허용과 회원의 익명 리뷰 허용을 따로 정한다(기본값은 모두 비허용). 링크 제한, 신고, 관리자 삭제를 둔다.
- **스팀 방식의 평가 등급:** 추천/비추천 비율로 평가 등급을 계산해 카드, 목록, 상세에 표시한다.
- **댓글과 리뷰 반응:** 리뷰와 별개로 평가에 영향을 주지 않는 댓글(작성자 외 다른 회원끼리도 답글 가능, 서비스별 익명 허용 설정)을 두고, 리뷰마다 추천/비추천과 추천순·최신순 정렬을 둔다.
- **분류와 표기:** 서비스 용도, 프로젝트 유형(토이/사이드/정식 서비스), 기기 지원(PC/모바일), 가격(무료/유료/일부 유료), 등록 주체(개인/팀), 지원 언어, 이용 형태, 운영 상태를 표기하고, 이용 형태를 뺀 항목은 필터로 고를 수 있다.
- **AI 자연어 검색:** 목적을 문장으로 입력해 서비스를 찾는다. 일반 검색을 먼저 완료한 뒤 구현한다.
- **사이트 안에서 바로 이용(확장):** 등록자가 선택하는 내부 연결 방식. 쥬니버처럼 사이트 안에서 바로 이용하는 경험을 제공한다.

### 6.3 알려진 한계와 위험

- **초기 서비스 부족:** 한모아도 최근에야 첫 외부 제작자가 등록되었다. 서비스가 적으면 사용자가 올 이유가 없다. 자세한 대응은 7번에서 다룬다.
- **반응 조작:** 투표 중심 플랫폼에서 봇과 유료 투표로 순위가 왜곡되었다는 창업자들의 후기가 있다(부록 B). 인기 점수 기준과 이상 징후 시 집계를 중단하는 규칙이 필요하다. (일부 창업자의 후기이며 표본은 작다)
- **일반 사용자 유입:** 제작자끼리만 보는 플랫폼이 되면 같은 문제가 생긴다.
- **외부 링크 안전:** 악성·부적절 사이트에 대한 신고와 숨김 처리가 필요하다.
- **스팸·악성 리뷰:** 비회원 리뷰나 익명 리뷰를 허용하면 스팸, 비방, 욕설이 달릴 수 있다. 링크 제한, 신고, 관리자 삭제를 둔다(부록 C).

## 7. 초기 사용자 확보 전략과 위험

### 7.1 문제

서비스가 있어야 사용자가 오고, 사용자가 있어야 제작자가 등록한다. 가장 큰 문제로 보고, 성패는 마케팅에 달려 있다고 판단한다.

### 7.2 전략

- Instagram을 돌아다니며 제작자에게 직접 서비스 등록을 유도한다.
- Instagram으로 마케팅해 사용자를 유입시킨다. SNS는 마케팅과 유입을, WEBTER는 이용과 반응을 맡는 구조(3.2)를 따른다.

### 7.3 초기 서비스 확보 계획

- 작성자가 만든 서비스 2개와 주변에서 받은 서비스 2~3개를 등록한다. 목표 수치는 미정이다.
- 부족하면 시연용 샘플 데이터로 채운다. 이 경우 샘플임을 구분해서 밝힌다.

### 7.4 위험

- 등록 서비스가 적으면 AI 자연어 검색이 일반 검색보다 유용하지 않을 수 있다.
- 초기에는 반응(리뷰·좋아요·저장)이 적어 인기 순위와 평가 등급이 의미를 갖기 어렵다.
- 마케팅 성과를 측정할 기준(등록 서비스 수, 실행 클릭 수 등)은 아직 정하지 않았다.

## 8. 수익 모델 (검토)

현재 개발 범위에는 수익 기능을 포함하지 않는다. 아래는 검토 후보이다. 출시 후 **월 전체 운영비 예산은 3~7만 원**이며, 앱·DB·파일 저장·전송·외부 검사·AI API 등을 합산한다. 예산 충족 여부와 실제 비용은 아직 검증하지 않았다.

**수익 방향(가설):** 일반 사용자를 끌어들이는 것이 광고 수익의 전제이므로, 바이브 코딩으로 만든 가벼운 웹 서비스를 앞세워 일반 사용자의 유입을 늘리고 광고를 노출한다. 제작자에게는 광고 상품(상단 노출 등)을 제공한다. 구체적인 모델은 개발을 마친 뒤 발표를 준비할 때 정한다.

| 후보 | 내용 | 참고 사례 | 유의할 점 |
|---|---|---|---|
| 사이트 내 광고 | 서비스 목록과 구분된 광고 영역 | 한모아(광고 수익 배분을 준비 중), 바이브마트(애드센스·쿠팡 파트너스) | 광고임을 표기하고 이용 경험을 해치지 않아야 한다 |
| 후원 | 이용자의 자율 후원 | 바이브마트 | 수익이 작고 불확실하다 |
| 유료 상단 노출 | 비용을 내고 서비스를 상단에 노출 | 배달 앱의 광고 노출 방식 | 순위의 신뢰를 해칠 수 있다. 일반 순위와 분리하고 광고 표기가 필요하다 |
| 개발자 대상 광고 | 제작자가 모이면 해커톤, 강의, 채용 등 관련 업체의 광고 | - | 제작자가 충분히 모인 뒤에야 가능하다 |

## 9. 기대효과

정량 목표는 정하지 않고 정성적 효과만 기술한다.

- **사용자:** 흩어진 웹 서비스를 모아 놓은 곳에서 새로운 서비스를 탐색하고, 설치 없이 바로 이용한다. 부담 없이 구경하고 즐기는 공간이 된다.
- **제작자:** 서비스를 한 번 등록해 노출하고, 서비스별 반응(조회수, 리뷰, 좋아요, 저장)을 한곳에서 확인하며 운영 상태를 관리한다. 마케팅으로 유입을 만드는 일은 SNS가 맡는다. 앱스토어처럼 반응을 확인할 수 있어 포트폴리오의 근거로 활용할 수 있다. (가설)
- **플랫폼 구조:** SNS는 홍보 채널로 유지되고, WEBTER가 이용과 반응의 연결 지점이 된다.
- **연계 노출 효과(가설):** 한 서비스를 보러 온 사용자가 다른 서비스도 함께 접한다.
- **부가 효과(장기):** 채용 담당자나 협업 상대가 서비스를 보고, 제작자 프로필의 외부 링크를 따라가 연락할 수 있다.

| MVP | 구글 소셜 로그인, 계정(아이디·닉네임·프로필 사진), 관심 카테고리, 기본 반응형 / 홈(트렌딩·인기·최신 요약, 관심 카테고리가 있으면 해당 카테고리의 트렌딩·인기 우선 표시), 카테고리, 서비스 용도 카테고리 줄, 필터(유형·기기·가격·등록 주체·지원 언어·상태), 카드형·목록형 보기, 일반 검색, AI 자연어 검색(후순위·첫 출시 도입 재검토) / 서비스 상세(미리보기, 마크다운 소개와 서비스 정보, 버전 기록, 제작자 표시, 조회수, 실행 수, 평가 등급) / `이용하기`(새 탭, 카드·상세 공통), 소스 공개 서비스의 코드 아이콘 연결 / 서비스 등록·수정·삭제·운영 상태 관리, 등록 시 분류 선택과 주소 검증, 이미지 업로드(S3, 큰 이미지는 브라우저 압축) / 등록 후 URL 평판 조회·등록 글과 이미지의 AI 유해성 검사(방향 확정, 세부 미정), 비공개 서비스 이미지의 새 요청 제한(방향 확정, 세부 미정) / 서비스 단독 평가·리뷰(추천·비추천·미설정)와 리뷰 글 추천/비추천, 댓글, 제작자 답글, 좋아요, 저장 / 회원 기능 접근 시 로그인 안내와 로그인 후 원래 페이지로 복귀 / 마이페이지 / 제작자 프로필(기본 정보, 외부 링크, 서비스 개수, 받은 좋아요, 등록한 서비스 목록) / 신고 접수와 자동 임시 비공개, 관리자 페이지(신고·임시 비공개 목록, 복구·최종 비공개·삭제·기각 처리, 회원 제재 지정, 조치 이력) / 모바일 접속 시 모바일 지원 필터 토글 / 링크 공유 미리보기(OG)와 링크 복사 / 약관·개인정보처리방침 페이지(임시) |
| 화면 구현·서버 연동 예정 | 알림 화면은 목업이다. 서버 누적 조회·9종 알림·답글 위치 이동·팀원 초대는 후속이며 푸시·엄격한 실시간 갱신은 제외한다 |
| 구현 예정(로그인·회원·알림 이후) | 서비스별 아이디 검색·초대 수락·팀원 본인 서비스 연결. 등록자 제외 5명·등록자와 같은 권한(서비스 삭제·등록자 제거 포함). 등록자 탈퇴 시 팀원이 있는 서비스는 유지하고 먼저 수락한 팀원이 등록자 자리를 잇는다. 거절한 초대는 "거절함"으로 남기고 취소하면 초대와 알림을 삭제하며 재초대는 제한하지 않는다. 보낸 사람에게는 수락·거절 결과를 알린다. 팀원 서비스의 프로필 표시는 일반 서비스와 같은 공개 규칙을 따른다 |
| 확장 1순위 | 내부 연결(사이트 안에서 실행, 새 탭 병행, 첫 출시에는 포함하지 않음) |
| 확장 | 기존 확장 기능의 목록과 방향은 11.1을 따른다. 새 기능의 도입 방향·아이디어는 11.2, 현행 기능의 검토 과제는 11.3, SNS 유입 편의는 11.4에서 구분한다 |
| 제외 | 배포 전·출시 예정 서비스 등록, 제작 회고 글 작성 기능, 일반 커뮤니티 게시판, 소스 코드·이슈 관리, 서비스 직접 호스팅, 설치형 앱만 있는 서비스, 외부 서비스 내부 행동 측정, 자체 이메일 로그인(멘토 확인 후 재검토), 성인 콘텐츠 서비스 |

팔로우는 앱스토어처럼 특정 제작자를 구독하는 기능을 두지 않는 방향으로 MVP에서 제외하고, 대신 관심 카테고리를 설정해 홈에서 해당 카테고리의 트렌딩·인기 서비스를 우선 보여 준다.

### 10.2 한계

- 수요는 작성자의 경험에서 나온 가설이며 조사로 검증하지 않았다.
- WEBTER가 측정할 수 있는 행동은 서비스 상세 조회와 `이용하기` 클릭까지이며, 외부 서비스 안의 사용 시간이나 행동은 알 수 없다.
- 등록 서비스가 적은 초기에는 AI 자연어 검색, 인기 순위, 평가 등급의 효용이 낮을 수 있다.
- 운영 인력이 제한되어 있다. 즉시 등록·공개 후 URL 평판 조회와 등록 글·이미지의 AI 유해성 검사를 진행하는 방향이며, 신고와 관리자 숨김·삭제도 유지한다. 검사 제공자·실패·재시도·자동 숨김 기준은 미정이고 외부 사이트의 실제 브라우저 실행 검사는 이번 범위에 포함하지 않는다. 리뷰 스팸 AI 감지는 확장이다.
- 서비스를 비공개로 바꾸면 WEBTER가 제공하는 해당 이미지의 새 요청도 제한한다. 저장·전송·임시 URL·캐시 정책과 반영 시간은 미정이며, 이미 다운로드되거나 외부에 저장된 사본의 회수는 보장하지 않는다.
- 수익 모델은 개발 범위에 포함하지 않고 검토 후보로만 정리했다.

## 11. 확장 계획·아이디어·검토 과제

첫 출시 범위는 10.1과 정책서를 따른다. 이 장은 기존 확장 기능, 새로 제시한 도입 방향, 넣을지 고민하는 아이디어를 한곳에서 관리한다. **목적·도입 방향 확정과 첫 출시 포함·구현 완료는 구분한다.** 별도 결정이 없는 항목의 도입 시점·우선순위·세부 정책은 미정이며, 기록만으로 MVP를 추가하거나 기존 규칙을 변경하지 않는다.

### 11.1 기존에 정한 확장 기능

| 묶음 | 확장 방향과 범위 |
|---|---|
| 내부 연결 — 확장 1순위 | 사이트 안에서 서비스를 이용하는 방식. 새 탭 이용을 병행하며 첫 출시에는 포함하지 않는다. 방식·보안·삽입 제한은 부록 A에서 검토한다 |
| 등록·관리 편의 | 태그 추천, 등록 임시저장, 등록자의 공개·비공개 직접 전환. 직접 전환은 관리자 제한과 구분하며 공개 상태 필드는 MVP DB부터 포함한다. 태그 추천은 이름·설명·선택 용도와 기존 태그를 활용하는 규칙 방식을 기본 검토하고 AI 방식은 별도 확장으로 둔다 |
| 독립 오픈소스 영역 | GitHub 링크만 있는 서비스를 별도로 탐색한다. 런칭 이후 검토하며 현재 헤더·라우트·샘플은 제거했다. 홈·기본 목록·검색에서는 기본 제외하고 포함 방식은 확장 때 정한다. 이용 집계 없이 좋아요·저장으로 웹 서비스와 별도 인기 순위를 집계한다(정책서 4.10) |
| 로그인·계정 | 카카오·네이버·GitHub 등 추가 소셜 로그인과 계정 연동. 도입 시점, 연결·분리 정책은 미정이다 |
| 이용 환경 | PWA로 홈 화면 추가 등 모바일 이용 편의를 검토한다. 별도 데스크톱 앱 아이디어와 구분한다 |
| 제작자·프로필 | 등록 서비스와 활동을 보여 주는 공개 프로필 확장, 활동 레벨, 팔로우와 새 서비스 피드. 활동 레벨은 플랫폼 활동 수준을 표현하며 개발 실력 인증으로 쓰지 않는다. 팔로우는 MVP에서 제외한다 |
| 제작 과정·성과 표시 | 상세 페이지의 정해진 형식의 제작 이야기와 외부 개발 회고 링크, 공모전 수상작 표시. 웹터 안의 회고 글 작성 기능과 구분한다 |
| 서비스 통계·정렬 | 누적 인기 정렬, 일별 추이 등 제작자 상세 통계. 현재 제공하는 본인 서비스 요약 수치와 구분한다 |
| 등록 보조·운영 검사 | AI 서비스 설명 채워 주기, 리뷰 스팸 AI 감지, 신고 AI 판정, 도메인 소유 인증, 주기적 접속 점검. 첫 출시의 등록 후 URL 평판·글/이미지 검사 방향을 이 항목으로 옮기거나 제외하지 않는다 |
| 팀 고도화 | 역할 구분·역할 표시, 초대 만료. 현재는 아는 사람끼리 공동 운영하는 상황을 전제로 역할 부여·이전 규칙과 구현·사용 복잡도를 줄이기 위해 동일 권한을 주고 오남용 위험을 감수한다. 서비스별 초대·공동 관리·등록자 승계 자체는 이미 구현 예정인 기본 기능이다(정책서 4.11) |
| 수익 기능 | 광고·후원·유료 상단 노출 등 8장의 후보. 수익 기능은 현재 개발 범위에 포함하지 않는다 |

### 11.2 새 도입 방향과 확장 아이디어

| 항목 | 목적·아이디어 | 확정된 부분 | 남은 결정 |
|---|---|---|---|
| 아이디·닉네임 회원 검색 | 공개 아이디나 닉네임으로 회원을 찾고 프로필로 이동한다. 중복 닉네임은 아이디로 구별한다. 팀원 초대용 아이디 검색과 구분한다 | 도입 방향 | 첫 출시 포함 여부, 검색 위치·일치 방식·정렬·결과 범위 |
| SNS에서 서비스 상세로 쉽게 진입 | 인스타에서 관심을 가진 서비스의 웹터 상세로 바로 접근하고, 다른 서비스도 발견·이용하게 한다. 상세 링크 복사·QR·홍보 이미지 등을 검토한다(11.4) | 접근 편의·다른 서비스 발견이라는 목적 | 채택할 수단, 도입 시점, 기기·인스타 환경별 실제 단계와 효과 |
| 웹터에 대한 비공개 문의 | 웹터의 오류·불편·개선 의견을 운영자에게 비공개로 전달한다. 목적은 웹터 운영 개선이다 | 공개 서비스 제안과 목적·공개 범위를 분리 | 도입 여부·시점, 접수 수단, 답변·처리 방식. 기존 권리 침해·개인정보 문의 절차는 별도 관리 |
| 필요한 서비스의 공개 제안 공간 | 사용자가 필요한 서비스를 공개로 제안하고 제작자가 사용자 수요를 확인한다 | 비공개 운영 문의와 목적·공개 범위를 분리 | 도입 여부·시점, 작성·노출·운영 규칙. 투표·댓글·제작 연계는 미정. 일반 커뮤니티 게시판 제외 규칙과의 관계는 수요 제안 전용 범위로 검토 |
| 팀 기능 추가 고도화 | 기본 공동 관리 이후 역할과 운영 흐름을 발전시킬 여지를 검토한다. 기존 역할 구분·표시·초대 만료는 11.1에 둔다 | 고도화 여지를 별도로 관리 | 구체적인 기능·시점. 고정 조직형 팀과 이전 팀원 불러오기는 현행 범위에서 두지 않음 |
| 웹터 자체의 데스크톱 앱 | 웹터를 데스크톱 앱으로 제공하는 가능성을 검토한다. “왭터”는 대화 중 나온 명칭 아이디어다 | 확정 없음 — 아이디어 | 고유 가치, 대상 OS, 제공 방식·시점·명칭. 프로젝트명 변경이나 외부 데스크톱 앱 등록 허용을 뜻하지 않음 |
| 하위 세분화 카테고리 | 서비스가 늘면 하위 분류를 검토한다. 예: 게임 → 메타버스·힐링·공포·팀전/개인 | 확정 없음 — 아이디어 | 하위 카테고리·태그·별도 필터 중 구조 선택. 장르·경험과 참여 방식이 섞인 예시이므로 최종 계층으로 확정하지 않음. 현재 한 단계 용도·태그 구조 유지 |

### 11.3 도입 여부와 화면 구성을 검토할 항목

| 항목 | 검토 내용과 현행 기준 |
|---|---|
| 홈 검색창 중심 구성 | 현재는 큰 검색창·검색 예시 3개와 서비스 카드를 둔다. 검색창을 빼고 카드를 먼저 보이며 헤더 검색으로 대신할지 미정이다. 결정 전 현재 구성 유지 |
| 사이드바 역할 | 현재의 서비스 용도·저장한 서비스·내 서비스 관리 항목을 유지하면서 홈에서 맡을 역할과 구성을 재검토한다 |
| 직접 이미지 크롭·위치 조정 | 현재 자동 맞춤(꽉 채우기·전체 보이기)을 유지한다. 사용자가 직접 자르거나 프레임 안 위치를 옮기는 기능의 도입은 미정이다 |
| 등록 필수 항목 AI 일괄 채우기 | 서비스 주소 등에서 이름·소개·용도를 한꺼번에 채울지 검토한다. 개별 설명 작성 보조와 구분하며 결정 전 직접 입력 유지 |
| AI 자연어 검색의 첫 출시 도입 | 일반 검색 이후의 후순위 방향을 유지하되 도입 여부는 멘토링 뒤 결정한다. 현재는 모의 규칙이며 실패 시 일반 검색 대체 방식은 제안이다. 구현 방안·비용·한도는 [이슈 #27](https://github.com/p1001q/WEBTER/issues/27)에 정리했고 외부 AI API 사용 가능 여부·비용 부담·평가 비중을 확인한다 |
| 카드에서 바로 좋아요·저장 | 현재 카드는 수치만 표시하고 반응은 상세에서 한다. 카드에 직접 반응 버튼을 넣을지 미정이다 |
| 마이페이지 리포트 탭 | 내 서비스의 조회·이용하기 클릭·좋아요·저장·리뷰 흐름과 비교를 모아 볼지 검토한다. 받은 반응의 요약을 알림 대신 리포트에서 보는 방향이며 결정 전 현재 상위 탭 유지 |

### 11.4 인스타 유입 편의와 서비스별 공유 수단

- **문제와 목표:** 3.2의 댓글·팔로우 확인·DM 대기, 게시글 주소 캡처 후 인식, 프로필 링크에서 재탐색하는 과정을 줄인다. 유입 목적지는 웹터의 해당 서비스 상세이며, 사용자가 쉽게 `이용하기`를 찾고 다른 서비스도 탐색할 수 있게 한다.
- **공유 기능 후보:** 서비스별 상세 링크 복사, QR 생성 버튼·이미지 저장, QR·서비스명·소개를 담은 인스타 홍보 이미지 저장을 검토한다. QR만 추가해도 진입 단계가 줄어드는지는 별도로 확인한다.
- **QR 재생성 안:** 새 QR을 발급하면 이전 QR을 무효화하는 안이 있다. 이미 인스타에 올린 이미지의 코드가 더 이상 열리지 않을 수 있으므로 고정 주소 유지와 재발급·폐기·만료 안내 규칙은 미정이다. 자동으로 예전 홍보 이미지가 갱신되는 것은 아니다.
- **웹사이트에서 제공할 수 없는 동작:** 인스타 화면을 캡처한 순간을 웹터 웹사이트가 감지해 해당 사이트를 자동으로 여는 기능은 제공할 수 없다. QR 인식과 링크 열기는 인스타·OS·기기의 동작에 좌우된다. 데스크톱 앱 확장도 모바일 인스타의 이 동작을 자동으로 해결하는 전제가 아니다.
- **검토할 유입 경로:** 인스타 스토리의 링크 스티커에 해당 서비스 상세 주소를 넣는 방식은 댓글·팔로우·DM을 기다리지 않는 경로다. 웹터가 링크 복사·홍보 이미지 저장을 제공하더라도 게시자가 인스타에서 링크 스티커를 붙이는 과정은 남는다. 일부 지원 안드로이드 기기의 Circle to Search는 화면 속 QR을 캡처 없이 인식할 수 있지만 기기 공통 기능으로 보장하지 않는다.
- **확인 기준:** 실제 홍보물을 본 사용자가 상세에 도착하기까지의 조작 단계·대기, 상세에서 외부 서비스를 이용하는 흐름, 다른 서비스를 발견·이용하는 흐름을 확인한다. 측정 방식과 목표 수치는 미정이며 외부 서비스 내부 이용 시간을 측정할 수 있다고 표현하지 않는다.

참고: [Meta의 스토리 링크 스티커 안내](https://about.fb.com/ja/news/2021/10/linkaccessstickers/), [Android의 화면 속 QR 인식 안내](https://www.android.com/intl/en_uk/articles/how-do-you-scan-qr-codes-on-android/) (2026-11-05 확인). 안내를 근거로 해당 기능을 웹터에서 구현·검증했다고 표현하지 않는다.

## 부록 A. 내부 연결(사이트 안에서 실행) 검토

쥬니버처럼 사이트 안에서 바로 서비스를 이용하는 경험을 위해, 외부 사이트를 WEBTER 화면 안에 삽입하는 방식을 검토했다. MVP에서는 실행 주소 하나를 받아 외부 연결(새 탭)만 제공하고, 내부 연결은 확장 1순위로 둔다.

### A.1 방식

- 등록자가 서비스마다 연결 방식을 선택한다. 기본값은 외부 연결이다.
- 내부 연결을 고른 서비스도 `새 탭으로 크게 보기` 버튼을 함께 제공한다. 큰 화면으로 즐기고 싶은 경우를 위해서다.
- 나중에 다시 이용하려는 경우의 즐겨찾기는 기존 `저장` 기능으로 처리한다.
- 내부 연결은 첫 출시에서 제외한다. 연결 방식 필드와 내부 실행 화면의 설계·구현은 확장 단계에서 검토한다.
- 내부 연결을 도입하면 상세 페이지에 설명 탭(미리보기 이미지)과 이용 탭(사이트 화면)을 두고 전환한다.

### A.2 삽입 가능 여부 확인

- 삽입 가능 여부는 AI 없이 확인할 수 있다. 등록 시 서버가 주소로 요청을 보내 삽입을 막는 응답 헤더(`X-Frame-Options`, CSP `frame-ancestors`)가 있는지 읽는다.
- 헤더로 알 수 없는 문제가 있다. 자바스크립트로 삽입을 막는 사이트, 로그인·쿠키가 필요한 서비스의 오작동, 모바일 키보드와 전체 화면 문제이다. 등록자가 미리보기로 직접 확인하는 단계를 둔다.
- GitHub 파일 보기 주소(소스 보기 주소)는 삽입이 막힌다. 이런 주소를 입력하면 배포된 주소를 입력하도록 안내한다.

## 부록 C. 리뷰 운영과 반응 지표

### C.1 리뷰 정책

- 서비스에 글 없이 추천·비추천만 남길 수 있고 이후 리뷰를 작성해 같은 평가 한 건을 공유한다. 중복 집계하지 않는다. 리뷰 작성 후 평가 버튼으로 변경하려 하면 리뷰 수정 여부를 묻고, 수정 창의 저장 성공 후에만 바꾼다. 글 없는 평가의 취소는 가능하나 비회원·제작자 본인·운영 중지에서는 단독 평가를 허용하지 않는다.
- 리뷰는 의견 글과 평가 상태(추천/비추천/미설정)로 이루어진다. 회원은 세 가지 상태를 모두 쓸 수 있고, 비회원은 "미설정"으로만 쓸 수 있다.
- 서비스 등록자가 서비스마다 (1) 비회원 리뷰 허용, (2) 회원의 익명 리뷰 허용을 따로 설정한다. 기본값은 둘 다 비허용이다.
- 비회원은 IP 주소로 같은 사람인지 구분한다. IP는 원문 대신 해시로 저장하고, 비회원 리뷰에는 IP 일부만 표시한다(IPv4 예: `123.45`, 전체 IP는 표시하지 않음). 중복 방지용 전체 IP의 HMAC과 공개 표시용 일부 IP를 따로 저장한다(제안). 개인정보 처리방침에 수집·표시 항목으로 적고 법적 확인이 필요하다.
- 스팸·비방·욕설 가능성을 안내하고 리뷰·댓글·답글의 링크를 금지한다. 익명 여부는 작성 시 정하고 수정 시 바꾸지 않는다. 신고·관리자 삭제를 둔다.
- 제작자가 본인 서비스에 리뷰를 쓰면 "제작자" 표시가 붙고 평가 상태는 없으며, 평가 집계와 인기 점수에서 제외한다. 본인 서비스에는 좋아요와 저장을 할 수 없다.
- 다른 회원이 리뷰에 추천/비추천을 남길 수 있고(본인 리뷰 제외, 서비스 평가 집계와 무관), 리뷰 목록은 추천순(기본)과 최신순을 고른다.
- 댓글은 리뷰와 별개다. 평가 비율·등급·인기 점수에 영향을 주지 않고, 추천·비추천은 없으며 신고할 수 있다. 서비스 등록자가 서비스마다 익명 댓글 허용을 정한다(기본값 비허용). 작성자 외 다른 회원끼리도 댓글·답글을 달 수 있다. 정책서 6.4를 따른다.
- 서비스 제작자만 다른 사람의 리뷰에 답글을 달 수 있다. 다른 사용자는 답글을 달 수 없다. 앱스토어의 개발자 응답처럼 리뷰당 1개를 제안하며, 답글도 신고와 관리자 삭제의 대상이다.

마이페이지는 내 서비스 / 저장한 서비스 / 리뷰·댓글 / 계정 설정이며 리뷰·댓글은 하위 탭으로 나눈다. 내 서비스는 등록일 최신·과거·전체 인기순, 저장 목록은 저장 시각 최신·과거순이다. 두 목록은 운영 중지도 기본 포함하고 비공개 저장은 이미지·사유·상세를 숨긴 채 해제만 허용한다. 서비스 단독 평가는 목업이고, 리뷰 글 반응·정렬은 요구사항으로 남아 있다.

### C.2 평가 등급

스팀의 평가 방식을 참고한다. 추천 비율 = 추천 수 / (추천 수 + 비추천 수)이며, 미설정·제작자 리뷰는 비율에서 제외하고 단독 평가와 리뷰 평가는 회원·서비스당 한 번만 센다.

| 조건 | 표시 |
|---|---|
| 추천+비추천 5개 미만 | 평가 수 부족 |
| 5~19개 | 긍정적 / 복합적 / 부정적 |
| 20개 이상 | 80~100% 매우 긍정적, 70~79% 대체로 긍정적, 40~69% 복합적, 20~39% 대체로 부정적, 0~19% 매우 부정적 |

숫자는 초기값이며 등록 서비스가 늘면 조정한다.

### C.3 AI 스팸·욕설 필터 (확장)

- 1차는 규칙(링크 제한, 도배 제한, 금지어)으로 막는다.
- AI는 의심 리뷰를 숨기고 관리자 검토로 넘기는 보조 역할로 쓴다.
- AI는 오탐, 비용, 응답 지연이 있다. 이 기능은 MVP 밖의 확장으로 둔다.

### C.4 반응 지표 정의

- **조회수:** 서비스 상세 페이지를 연 횟수. 화면에 표시만 하고 인기 점수에는 넣지 않는다. 제작자 본인 조회는 집계하지 않는다.
- **실행 수:** `이용하기` 버튼을 누른 횟수. 모든 클릭을 집계하되, 같은 회원 또는 IP가 같은 서비스를 1분 안에 10회 이상 또는 5분 안에 20회 이상 클릭하면 그 서비스의 클릭을 1시간 동안 집계에서 제외한다. 제작자 본인 클릭은 집계하지 않는다.
- **인기 점수:** 이용하기 클릭, 좋아요, 저장으로 계산한다. 리뷰는 점수에 넣지 않고 평가 등급으로 따로 표시한다.
- **등록·운영 한도:** 하루 서비스 등록은 5개, 신고 자동 임시 비공개는 런칭 초반 서로 다른 회원 4명(규모가 커지면 상향), 아이디 변경은 14일 내 2회다. 구분: 확정(2026-11-04, M-75·M-78). 목업 상수와 서버 적용은 별도 작업이다.
- **트렌딩과 인기:** 트렌딩은 최근 3일 동안 반응이 몰린 서비스, 인기는 사용자가 기간(주간/월간/전체)을 골라 누적 반응으로 정렬한다.

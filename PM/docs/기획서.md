# WEBTER 프로젝트 기획서 v1.2

> 버전: 1.2
> 작성일: 2026-10-26 (v1.1: 2026-10-21)
> 서비스 범위와 정책의 세부 내용은 정책서(v1.1)를 따른다.

## 1. 프로젝트 개요

| 항목 | 내용 |
|---|---|
| 프로젝트명 | WEBTER (웹터) |
| 이름의 의미 | Web + 터. 웹 서비스를 모아 놓은 터. 장터, 놀이터처럼 여러 의미로 확장되는 한국어 이름 |
| 슬로건 | 웹에서 놀다, 웹터 |
| 한 줄 소개 | 개발자가 만든 웹 서비스를 한곳에서 발견하고, 설치 없이 바로 이용하며, 리뷰·좋아요·저장으로 반응을 남기는 웹 서비스 스토어 |
| 형태 | 데스크톱과 모바일을 고려한 반응형 웹 (PWA는 확장 기능) |
| 개발 기간 | 약 7주 (2026년 10.06(16)~11.25) |
| 팀 | 얼렁뚱땅 (박수연, 박성영) |

### 핵심 기능

- 서비스 탐색: 홈, 트렌딩·인기·최신, 카테고리, 필터, 검색, 관심 카테고리, 카드형·목록형 보기
- 외부 웹 서비스 실행: `이용하기` 버튼으로 새 탭에서 실행, 소스를 공개한 서비스는 코드 아이콘(`</>`)으로 연결
- 서비스 등록 및 관리: 서비스 링크(선택적으로 GitHub 링크)를 등록, 사용 상태 관리, 버전 기록
- 회원 반응: 리뷰(추천/비추천/미설정)와 리뷰 추천/비추천, 댓글, 좋아요, 저장. 스팀 방식의 평가 등급 표시
- 소셜 로그인 기반의 단일 회원 체계: 이용자와 개발자를 구분하지 않음
- AI 활용: 자연어 검색으로 서비스 탐색을 돕는 기능 (MVP 후순위, 일반 검색을 먼저 완료한 뒤 구현)

## 2. 배경과 문제

### 2.1 배경

- AI 개발 도구와 바이브 코딩이 확산되면서 개인이나 소규모 팀도 웹 서비스를 빠르게 만들고 배포할 수 있게 되었다.
- 그러나 서비스를 만든 뒤 사용자를 모으고 반응을 확인하는 과정은 여전히 여러 채널로 나뉜다.

### 2.2 사용자가 겪는 문제

- 흥미로운 웹 서비스를 SNS 알고리즘 추천으로만 접하게 된다. 원하는 서비스를 능동적으로 찾을 경로가 없다.
- 서비스를 소개하는 홍보 계정을 따라가거나, 게시물을 타고 들어가 링크를 받아야 한다.
- 서비스에 대한 반응이 댓글에 흩어져 있어 확인이 번거롭고, 결국 보지 않게 된다.
- SNS는 주로 모바일에서 쓰는데 웹 서비스는 PC에서 쓰고 싶은 경우가 많아, 모바일에서 웹으로 옮겨 가는 과정이 불편하다.

### 2.3 아이디어 발전 과정

| 단계 | 관찰과 판단 |
|---|---|
| 1 | 바이브 코딩으로 웹 서비스 제작 접근성이 높아졌다 |
| 2 | Instagram 게시물과 자동 DM 등으로 서비스를 홍보하고 링크를 전달한다 |
| 3 | 홍보, 서비스 정보, 반응이 SNS 안에서 뒤섞이거나 여러 채널로 분산된다 |
| 4 | SNS는 홍보와 유입을 맡고, 별도 플랫폼이 등록·탐색·피드백을 맡는 구조를 구상했다 |
| 5 | 디스콰이엇 등 유사 서비스의 운영 사례를 확인하고 웹 서비스 스토어 관점에서 발전 가능성을 검토했다 |

### 2.4 해결하려는 문제와 해결 방향

| 문제 | 현재 상황 | 해결 방향 |
|---|---|---|
| 발견 | 독립 웹 서비스가 SNS·커뮤니티에 흩어져 있어 찾기 어렵다 | 카드형·목록형 보기, 상세 페이지, 정렬별 탐색 |
| 이용 연결 | 홍보 게시물에서 실제 서비스까지 이동 경로가 일정하지 않다 | 상세 페이지의 `이용하기` 버튼으로 외부 서비스에 바로 연결 |
| 운영 | 제작자가 소개·링크·사용 상태를 여러 채널에서 관리한다 | 등록, 수정, 상태 관리를 한 화면에 모음 |
| 피드백 | 댓글·DM·설문에 반응이 분산된다 | 서비스 상세 페이지에 리뷰 공간을 둠 |

### 2.5 검증 상태

- 사용자 쪽 문제는 작성자의 직접 경험에서 나왔고, 제작자 쪽 문제(운영·피드백 분산)는 작성자의 추정이다. 둘 다 별도의 수요 조사로 검증하지 않았다.
- 유사 서비스(디스콰이엇 등)의 운영은 이런 서비스의 수요 가능성을 보여주지만, WEBTER의 수요가 검증되었다는 의미는 아니다.

## 3. 해결 방식과 핵심 가치

### 3.1 해결 방식

WEBTER는 웹 서비스를 한곳에 모아 보여 주고, 설치 없이 바로 이용하도록 연결하는 웹 서비스 스토어다. 지금 바로 이용할 수 있는 서비스만 모은다.

- **모으기:** 제작자가 배포한 웹 서비스의 링크(선택적으로 GitHub 링크)를 등록하고 관리한다
- **찾기:** 홈(트렌딩·인기·최신), 카테고리, 검색으로 탐색한다. 검색어를 정확히 모르면 목적을 문장으로 입력하는 AI 자연어 검색을 쓴다(MVP 후순위)
- **이용하기:** 상세 페이지나 카드(데스크톱 hover)에서 `이용하기`를 누르면 외부 서비스가 새 탭에서 열린다
- **반응 남기기:** 회원은 리뷰(추천/비추천/미설정), 좋아요, 저장으로 반응을 남기고 다른 회원의 리뷰에 추천/비추천을 남길 수 있다. 등록자가 허용한 서비스에는 비회원도 리뷰를 남길 수 있다. 리뷰와 별개로 댓글로 서비스에 대해 이야기를 나눌 수 있다

### 3.2 SNS와의 관계

일반 사용자는 Instagram, YouTube 같은 SNS를 압도적으로 자주 사용하므로, 마케팅과 유입은 SNS가 맡는 구조가 자연스럽다. WEBTER는 SNS를 대체하지 않고, 유입된 사용자가 서비스를 실행하고 상태를 확인하고 반응을 남기는 곳을 맡는다.

| 영역 | 담당 역할 | 사용자 흐름 |
|---|---|---|
| SNS | 홍보와 관심 유도 | 홍보 게시물에서 WEBTER 상세 페이지로 이동 |
| WEBTER | 서비스 등록, 실행 연결, 상태 관리, 반응 관리 | 서비스를 비교하고 정보를 확인한 뒤 이용 여부 결정 |
| 외부 웹사이트 | 실제 서비스 실행 | `이용하기`로 새 탭에서 사용 |

**연계 노출 효과(가설):** SNS 게시물은 서비스 하나 단위로 노출되지만, WEBTER에서는 한 서비스를 보러 온 사용자가 목록, 카테고리, 다른 서비스 카드를 통해 다른 서비스도 함께 접하게 된다. Steam 같은 스토어형 플랫폼에서 하나를 찾다가 다른 항목도 둘러보게 되는 경험과 같은 효과를 기대한다.

### 3.3 핵심 가치

- **발견:** 흩어진 웹 서비스를 한곳에서 탐색한다
- **즉시 이용:** 설치나 이동 과정 없이 바로 이용한다
- **등록과 홍보:** 제작자가 서비스를 등록하고 사용자에게 노출한다
- **반응:** 사용자는 반응을 남기고, 제작자는 서비스별 반응을 확인한다
- **서비스 중심:** 개발자 개인보다 개발자가 만든 서비스를 중심으로 보여 준다

### 3.4 동작 원칙

- MVP에서는 서비스 링크를 등록받아 새 탭에서 열며(소스를 공개한 서비스는 GitHub 링크도 받아 아이콘으로만 연결), 직접 호스팅하거나 iframe으로 실행하지 않는다(사이트 안에서 바로 실행하는 내부 연결은 확장 1순위, 부록 A). 이유는 다음과 같다.
  - 외부 서비스의 보안 정책으로 iframe 실행이 제한될 수 있다
  - 외부 서비스의 로그인, 결제, 개인정보 처리 책임을 WEBTER와 분리할 수 있다
  - 구현 범위를 줄이고 다양한 웹 서비스를 연결할 수 있다
- 카드 본문을 누르면 상세 페이지로 이동하고, `이용하기`(데스크톱에서 카드에 마우스를 올리면 나타남)를 누르면 외부 사이트를 연다. 카드의 `이용하기` 클릭도 상세 페이지와 같은 실행 수로 집계한다
- 소스 코드 관리나 종합 프로젝트 관리 기능은 범위에서 제외한다
- 배포 전 서비스는 받지 않는다. 사용자가 바로 이용할 수 있는 서비스만 모은다
- WEBTER가 측정할 수 있는 행동은 `이용하기` 클릭과 서비스 상세 조회까지다

## 4. 서비스 분류와 탐색 구조

### 4.1 분류 기준

서비스는 아래 표의 다섯 가지 기준과 이용 형태, 지원 언어로 분류한다. 이용 형태는 등록자가 입력한 링크에 따라 정해지고, 나머지는 등록자가 직접 선택한다.

- 이용 형태: 웹 서비스 / 오픈소스(확장, GitHub 링크만 있는 서비스). 내부 연결(사이트 안에서 이용)은 확장이다. 웹 서비스에 GitHub 링크를 함께 입력하면 소스 공개 서비스로 코드 아이콘이 표시된다.
- 지원 언어: 한국어 / 영어(복수 선택, 기본값은 한국어)

| 기준 | 값 | 비고 |
|---|---|---|
| 서비스 용도 | 놀이, 생활, 학습, 생산성, 디자인·창작, 유틸리티, 개발자 도구, 기타 | 복수 선택 가능. 소분류는 태그가 대신한다 |
| 프로젝트 유형 | 토이 프로젝트 / 사이드 프로젝트 / 정식 서비스 | 만든 목적과 운영 계획으로 구분 |
| 기기 지원 | PC / 모바일 (복수 선택) | 모바일은 반응형, 웹앱 등 모바일에서 불편 없이 쓸 수 있으면 해당 |
| 가격 | 무료 / 유료 / 일부 유료 | |
| 등록 주체 | 개인 / 팀 | 팀이면 팀명을 입력 |

### 4.2 프로젝트 유형 정의

| 유형 | 만든 목적 | 운영 계획 |
|---|---|---|
| 토이 프로젝트 | 학습, 재미, 실험 | 지속 운영 계획 없음 |
| 사이드 프로젝트 | 사용자에게 제공할 의도가 있음 | 운영을 이어갈 계획이 있음 |
| 정식 서비스 | 본업이나 창업으로 운영하는 서비스(팀·회사 포함) | 지속 운영 |

### 4.3 탐색 방식

- 사용자는 서비스 용도, 프로젝트 유형, 기기 지원, 가격, 등록 주체, 지원 언어, 사용 상태를 선택해 서비스를 골라 볼 수 있다. 예를 들어 놀이, 팀, 모바일 지원 서비스만 모아 볼 수 있다. 가장 자주 쓰는 서비스 용도는 필터 패널이 아니라 목록 위 가운데의 카테고리 줄에서 고르고, 이용 형태는 지금 고를 수 있는 값이 없어 필터로 두지 않는다.
- 서비스는 카드형과 목록형 중 하나를 골라 볼 수 있다. 카드형은 썸네일, 서비스 제목, 한 줄 소개, 좋아요 수, 저장 수를 보여 주고, 목록형은 아이콘, 서비스 제목, 한 줄 소개, 좋아요 수, 저장 수를 보여 준다(수치는 모바일에서도 항상 표시). 데스크톱에서 마우스를 올리면 카드 안에 평가 문구와 리뷰 수, `이용하기` 버튼이 나타나고, 모바일에서는 이용하기 버튼을 생략하고 평가 문구를 항상 표시한다.
- 모바일로 접속하면 모바일에서 바로 즐길 수 있는 서비스가 먼저 보이도록 "모바일 지원 서비스만 보기" 토글이 켜진 상태로 시작한다.
- 토글을 끄면 PC 전용 서비스도 볼 수 있다. 모바일에서 PC 전용 서비스를 발견하면 저장해 두었다가 PC에서 이용할 수 있다.
- PC로 접속하면 토글을 보여 주지 않고, 기기 지원을 포함한 필터와 검색으로 탐색한다.
- 사용자가 관심 카테고리를 설정하면 홈에서 해당 카테고리의 트렌딩·인기 서비스를 우선 보여 준다.
- 서비스 용도는 복수로 선택할 수 있고, 세부 분류는 태그가 맡는다. 등록할 때 이름과 설명을 보고 태그를 추천해 주는 기능은 확장이다.
- 서비스에는 등록자가 바꿀 수 있는 사용 상태(사용 가능/사용 불가능)가 있다. 사용 불가능이면 사유를 한 줄로 적어 서비스 상단에 보여 주고, 기본 목록에서는 숨긴다. 필터에서 선택하면 볼 수 있고, 필터의 기본값은 "사용 가능"이다. 사용 불가능 서비스에도 좋아요·저장은 가능하고, 리뷰는 추천·비추천 없이 쓸 수 있다.
- WEBTER는 기본 반응형 웹으로 개발해 모바일 접속에서도 화면이 깨지지 않게 한다.

### 4.4 서비스 이미지

한 서비스에는 세 종류의 이미지가 쓰이며, 모두 선택 입력이다.

| 이미지 | 용도 | 규칙 |
|---|---|---|
| 아이콘 | 목록형 보기 | 정사각형 |
| 썸네일 | 카드형 보기 | 카드 비율로 잘라서 등록 |
| 미리보기 | 상세 페이지 | 최대 8장. 서비스마다 가로 16:9 또는 세로 9:16 중 하나로 통일. 이미지 맞춤은 "꽉 채우기"(직접 조정해 자르기)와 "전체 보이기" 중 선택 |

아이콘과 썸네일을 올리지 않으면 선택한 서비스 용도별 기본 이미지를 보여 주고, 미리보기를 올리지 않으면 해당 영역은 생략한다.

### 4.5 확장 후보

- 팀원(공동 작업자) 추가: 팀 서비스에 회원을 계정 아이디로 추가하고 수정·관리 권한을 공유한다. MVP에서는 개인 또는 팀명 입력까지만 제공한다.
- PWA: 홈 화면 추가 등 앱에 가까운 모바일 경험. 구현 비용이 작으면 추가한다.
- 제작 이야기: 상세 페이지에 정해진 형식의 짧은 설명과 개발 회고 외부 링크를 연결한다.
- 공개·비공개 직접 전환: 등록자가 자기 서비스를 직접 비공개로 바꾸고 다시 공개로 되돌린다. 관리자가 건 비공개와 구분해야 하며 구분 방식은 확장 때 정한다. 공개 상태 필드는 MVP DB부터 포함한다.
- 오픈소스 서비스 영역: GitHub 링크만 있는 서비스를, 화면 최상단 오른쪽의 코드 아이콘(`</>`)으로 들어가는 별도 영역에서 보여 준다. 일반 사용자에게는 눈에 띄지 않게 두고, 홈·기본 목록·검색에서는 제외하며 별도의 설정으로만 포함된다(이용 형태 필터를 두지 않아 포함 방식은 확장 때 정한다). 이용 집계 없이 좋아요와 저장으로 웹 서비스와 따로 인기 순위를 집계한다(정책서 4.10).
- 공모전 수상작 표시

## 5. 대상 사용자

### 5.1 주 타깃

일반 사용자와 제작자가 모두 주요 사용자이며, 서비스를 이용하는 일반 사용자를 먼저 고려한다.

이 서비스의 출발점은 SNS(Instagram)에서 서비스를 소개받아도 실제 이용으로 이어지기 어렵다는 경험이다. SNS는 주로 모바일에서 서비스를 둘러보는 용도로 쓰이고, 실제로 이용하려면 링크를 찾고 웹으로 이동하는 등 몇 단계를 거쳐야 한다. 단계가 적더라도 번거로우면 이용까지 가지 않는다. WEBTER는 발견에서 이용까지의 단계를 줄이는 데 초점을 둔다.

### 5.2 사용자 구분

| 구분 | 대상 |
|---|---|
| 서비스를 이용하는 사용자 | 새로운 웹 서비스를 발견하고 싶은 일반 사용자, 웹게임·인터랙티브 콘텐츠를 찾는 사용자, 문제를 해결할 웹 도구를 찾는 사용자, 다른 개발자의 서비스를 체험하려는 개발자 |
| 서비스를 등록하는 사용자 | 누구나 서비스를 등록할 수 있다. 독립 개발자, 학생, 초보 개발자, 사이드 프로젝트 개발자, 바이브 코딩으로 만든 제작자, 소규모 팀 등. 숙련도나 제작 방식으로 등록을 제한하지 않는다 |
| 장기 확장 사용자 | 결과물을 보고 개발자를 찾는 채용 담당자, 협업할 개발자나 프로젝트를 찾는 사용자, 새로운 서비스에 관심 있는 투자자·기획자 |

### 5.3 회원 구조

회원가입 시 일반 사용자와 개발자를 구분하지 않는 단일 회원 체계를 쓴다. 한 사람이 이용자와 제작자 역할을 오갈 수 있다는 실제 사용 방식을 반영한 결정이다. 로그인은 소셜 로그인(구글, 카카오)으로만 제공하며, 시간이 되면 네이버와 GitHub를 추가한다. 계정에는 중복 불가이며 변경할 수 있는 아이디(공개 식별자)와 중복이 가능한 닉네임을 설정한다.

가입은 별도 화면 없이 사용 흐름 안에서 이루어진다. 비회원으로 둘러보다가 회원 기능(리뷰 평가, 좋아요, 저장, 서비스 등록, 신고 등)을 누르면 로그인 안내가 나오고 로그인 화면으로 이동한다. 소셜 로그인(신규는 회원가입)을 마치면 온보딩(약관 동의, 아이디·닉네임 설정, 관심 카테고리 선택은 건너뛰기 가능)을 거쳐, 사용자가 보던 페이지로 되돌아간다.

| 사용 상태 | 가능한 행동 |
|---|---|
| 비회원 | 목록·상세 조회, 검색, 카테고리 탐색, 외부 서비스 실행, 등록자가 비회원 리뷰를 허용한 서비스에 평가 상태 없는 리뷰 작성 |
| 회원 | 비회원 기능 + 모든 서비스에 리뷰(추천/비추천/미설정), 리뷰 추천/비추천, 댓글, 좋아요, 저장 |
| 서비스 등록 회원 | 회원 기능 + 서비스 등록·수정·삭제 및 사용 상태 관리 |

### 5.4 제작자 프로필과 외부 연결

- 서비스 상세 페이지에는 제작자의 프로필 사진과 이름이 표시되고, 누르면 제작자 프로필로 이동한다. 카드에는 제작자를 표시하지 않는다.
- 제작자 프로필에는 프로필 사진, 닉네임, 아이디, 한 줄 소개, 블로그·GitHub·Instagram·Velog·포트폴리오 등 외부 링크, 등록한 서비스 개수, 받은 좋아요 수, 등록한 서비스 목록이 표시된다. 외부 링크 연결은 MVP에 포함한다. 팔로워 수는 표시하지 않고, 활동 레벨은 확장 기능이다.
- 제작 회고나 글을 쓰는 기능은 WEBTER에 만들지 않는다. 이미 회고를 쓸 수 있는 서비스가 많고, 회고를 궁금해하는 사람은 해당 서비스나 제작자에 관심이 큰 소수(주로 개발자)이기 때문이다. 이런 사용자는 외부 링크로 연결하면 충분하다. 다만 정해진 형식의 짧은 "제작 이야기"와 회고 외부 링크 연결은 확장 기능으로 검토한다.
- 플랫폼 안에 글 기능을 두면 서비스를 이용하려는 일반 사용자에게는 읽을 거리가 늘어 부담이 될 수 있다. WEBTER는 글이 아니라 서비스를 중심으로 연결된다.

### 5.5 향후 확장 방향

- 공개 프로필: 등록한 서비스와 활동을 보여 주는 포트폴리오 성격의 화면
- 활동 레벨: 개발 실력 인증이 아니라 플랫폼 활동 수준을 표현하는 방식으로만 검토
- 팔로우와 팔로우 피드: 특정 제작자의 새 서비스를 발견하는 기능. 앱스토어처럼 제작자를 구독하는 기능이 없으므로 MVP에서는 제외한다
- 채용 담당자, 협업 상대, 투자자·기획자와 제작자를 잇는 연결 기능

### 6.2 차별점

핵심 차별점은 다음 순서로 둔다.

1. **서비스 중심 구조:** 글, 회고, 커뮤니티 기능을 두지 않고 서비스 목록과 이용에 집중한다. 제작자 이야기는 프로필의 외부 링크로 연결한다.
2. **빠른 서비스 이용:** 상세 페이지의 `이용하기` 한 번으로 서비스가 열린다.
3. **웹 전용:** 설치형 앱이 아니라 웹 서비스만 대상으로 한다.

한모아와 비교하면 위 세 가지는 겹치는 부분이 있다. 그래서 다음 요소가 차이를 만든다.

- **로그인 없이 리뷰:** 서비스 등록자가 서비스마다 비회원 리뷰 허용과 회원의 익명 리뷰 허용을 따로 정한다(기본값은 모두 비허용). 링크 제한, 신고, 관리자 삭제를 둔다.
- **스팀 방식의 평가 등급:** 추천/비추천 비율로 평가 등급을 계산해 카드, 목록, 상세에 표시한다.
- **댓글과 리뷰 반응:** 리뷰와 별개로 평가에 영향을 주지 않는 댓글(작성자 외 다른 회원끼리도 답글 가능, 서비스별 익명 허용 설정)을 두고, 리뷰마다 추천/비추천과 추천순·최신순 정렬을 둔다.
- **분류와 표기:** 서비스 용도, 프로젝트 유형(토이/사이드/정식 서비스), 기기 지원(PC/모바일), 가격(무료/유료/일부 유료), 등록 주체(개인/팀), 지원 언어, 이용 형태, 사용 상태를 표기하고, 이용 형태를 뺀 항목은 필터로 고를 수 있다.
- **AI 자연어 검색:** 목적을 문장으로 입력해 서비스를 찾는다. 일반 검색을 먼저 완료한 뒤 구현한다.
- **사이트 안에서 바로 이용(확장):** 등록자가 선택하는 내부 연결 방식. 쥬니버처럼 사이트 안에서 바로 이용하는 경험을 제공한다.

### 6.3 알려진 한계와 위험

- **초기 서비스 부족:** 한모아도 최근에야 첫 외부 제작자가 등록되었다. 서비스가 적으면 사용자가 올 이유가 없다. 자세한 대응은 7번에서 다룬다.
- **반응 조작:** 투표 중심 플랫폼에서 봇과 유료 투표로 순위가 왜곡되었다는 창업자들의 후기가 있다(부록 B). 인기 점수 기준과 이상 징후 시 집계를 중단하는 규칙이 필요하다. (일부 창업자의 후기이며 표본은 작다)
- **일반 사용자 유입:** 제작자끼리만 보는 플랫폼이 되면 같은 문제가 생긴다.
- **외부 링크 안전:** 악성·부적절 사이트에 대한 신고와 숨김 처리가 필요하다.
- **스팸·악성 리뷰:** 비회원 리뷰나 익명 리뷰를 허용하면 스팸, 비방, 욕설이 달릴 수 있다. 링크 제한, 신고, 관리자 삭제를 둔다(부록 C).

## 7. 초기 사용자 확보 전략과 위험

### 7.1 문제

서비스가 있어야 사용자가 오고, 사용자가 있어야 제작자가 등록한다. 가장 큰 문제로 보고, 성패는 마케팅에 달려 있다고 판단한다.

### 7.2 전략

- Instagram을 돌아다니며 제작자에게 직접 서비스 등록을 유도한다.
- Instagram으로 마케팅해 사용자를 유입시킨다. SNS는 마케팅과 유입을, WEBTER는 이용과 반응을 맡는 구조(3.2)를 따른다.

### 7.3 초기 서비스 확보 계획

- 작성자가 만든 서비스 2개와 주변에서 받은 서비스 2~3개를 등록한다. 목표 수치는 미정이다.
- 부족하면 시연용 샘플 데이터로 채운다. 이 경우 샘플임을 구분해서 밝힌다.

### 7.4 위험

- 등록 서비스가 적으면 AI 자연어 검색이 일반 검색보다 유용하지 않을 수 있다.
- 초기에는 반응(리뷰·좋아요·저장)이 적어 인기 순위와 평가 등급이 의미를 갖기 어렵다.
- 마케팅 성과를 측정할 기준(등록 서비스 수, 실행 클릭 수 등)은 아직 정하지 않았다.

## 8. 수익 모델 (검토)

현재 개발 범위에는 수익 기능을 포함하지 않는다. 아래는 검토 후보이다.

**수익 방향(가설):** 일반 사용자를 끌어들이는 것이 광고 수익의 전제이므로, 바이브 코딩으로 만든 가벼운 웹 서비스를 앞세워 일반 사용자의 유입을 늘리고 광고를 노출한다. 제작자에게는 광고 상품(상단 노출 등)을 제공한다. 구체적인 모델은 개발을 마친 뒤 발표를 준비할 때 정한다.

| 후보 | 내용 | 참고 사례 | 유의할 점 |
|---|---|---|---|
| 사이트 내 광고 | 서비스 목록과 구분된 광고 영역 | 한모아(광고 수익 배분을 준비 중), 바이브마트(애드센스·쿠팡 파트너스) | 광고임을 표기하고 이용 경험을 해치지 않아야 한다 |
| 후원 | 이용자의 자율 후원 | 바이브마트 | 수익이 작고 불확실하다 |
| 유료 상단 노출 | 비용을 내고 서비스를 상단에 노출 | 배달 앱의 광고 노출 방식 | 순위의 신뢰를 해칠 수 있다. 일반 순위와 분리하고 광고 표기가 필요하다 |
| 개발자 대상 광고 | 제작자가 모이면 해커톤, 강의, 채용 등 관련 업체의 광고 | - | 제작자가 충분히 모인 뒤에야 가능하다 |

## 9. 기대효과

정량 목표는 정하지 않고 정성적 효과만 기술한다.

- **사용자:** 흩어진 웹 서비스를 모아 놓은 곳에서 새로운 서비스를 탐색하고, 설치 없이 바로 이용한다. 부담 없이 구경하고 즐기는 공간이 된다.
- **제작자:** 서비스를 한 번 등록해 노출하고, 서비스별 반응(조회수, 리뷰, 좋아요, 저장)을 한곳에서 확인하며 사용 상태를 관리한다. 마케팅으로 유입을 만드는 일은 SNS가 맡는다. 앱스토어처럼 반응을 확인할 수 있어 포트폴리오의 근거로 활용할 수 있다. (가설)
- **플랫폼 구조:** SNS는 홍보 채널로 유지되고, WEBTER가 이용과 반응의 연결 지점이 된다.
- **연계 노출 효과(가설):** 한 서비스를 보러 온 사용자가 다른 서비스도 함께 접한다.
- **부가 효과(장기):** 채용 담당자나 협업 상대가 서비스를 보고, 제작자 프로필의 외부 링크를 따라가 연락할 수 있다.

## 부록 A. 내부 연결(사이트 안에서 실행) 검토

쥬니버처럼 사이트 안에서 바로 서비스를 이용하는 경험을 위해, 외부 사이트를 WEBTER 화면 안에 삽입하는 방식을 검토했다. MVP에서는 실행 주소 하나를 받아 외부 연결(새 탭)만 제공하고, 내부 연결은 확장 1순위로 둔다.

### A.1 방식

- 등록자가 서비스마다 연결 방식을 선택한다. 기본값은 외부 연결이다.
- 내부 연결을 고른 서비스도 `새 탭으로 크게 보기` 버튼을 함께 제공한다. 큰 화면으로 즐기고 싶은 경우를 위해서다.
- 나중에 다시 이용하려는 경우의 즐겨찾기는 기존 `저장` 기능으로 처리한다.
- 등록 시 "연결 방식" 필드는 DB와 화면 설계에 미리 반영해 두고, MVP 포함 여부는 멘토 의견을 들은 뒤 결정한다.
- 내부 연결을 도입하면 상세 페이지에 설명 탭(미리보기 이미지)과 이용 탭(사이트 화면)을 두고 전환한다.

### A.2 삽입 가능 여부 확인

- 삽입 가능 여부는 AI 없이 확인할 수 있다. 등록 시 서버가 주소로 요청을 보내 삽입을 막는 응답 헤더(`X-Frame-Options`, CSP `frame-ancestors`)가 있는지 읽는다.
- 헤더로 알 수 없는 문제가 있다. 자바스크립트로 삽입을 막는 사이트, 로그인·쿠키가 필요한 서비스의 오작동, 모바일 키보드와 전체 화면 문제이다. 등록자가 미리보기로 직접 확인하는 단계를 둔다.
- GitHub 파일 보기 주소(소스 보기 주소)는 삽입이 막힌다. 이런 주소를 입력하면 배포된 주소를 입력하도록 안내한다.

### A.3 직접 확인한 응답 헤더 (2026-10-21)

| 주소 | 삽입 차단 헤더 | 판정 |
|---|---|---|
| GitHub 파일 보기 페이지 (`github.com/.../blob/...`) | 있음 (DENY, `frame-ancestors 'none'`) | 삽입 불가 |
| `hafandeals.vercel.app` (Vercel) | 없음 | 삽입 가능성 높음 |
| `ai-video-translator.com` (Vercel) | 없음 | 삽입 가능성 높음 |
| `vibemart.kr/camp.html` (Cloudflare) | 없음 | 삽입 가능성 높음 |
| `hanmoa.kr` | 있음 (DENY) | 삽입 불가 |
| `disquiet.io` | 있음 (SAMEORIGIN) | 삽입 불가 |

확인한 배포 사이트 3곳은 막힘이 없었지만 표본이 작아 "대부분 가능하다"고 단정할 수는 없다. 보안 설정을 직접 한 사이트는 막혀 있었다.

### A.4 위험과 완화

| 위험 | 완화 방안 |
|---|---|
| 악성 사이트가 WEBTER 도메인 안에서 실행되면 사용자가 WEBTER를 믿고 들어와 위험이 커진다 | 등록자 선택 방식, 신고와 관리자 숨김, iframe `sandbox` 적용 |
| 대상 사이트가 삽입을 막으면 실행되지 않는다 | 등록 시 헤더 자동 검사, 막히면 외부 연결만 허용 |
| 로그인·쿠키가 필요한 서비스가 iframe 안에서 오작동한다 | 등록자 미리보기, 새 탭으로 크게 보기 병행 |
| 모바일에서 키보드·전체 화면이 불편하다 | 새 탭으로 크게 보기 병행 |

### A.5 사례

쥬니버 게임랜드는 사이트 안에서 바로 게임을 실행했지만 Adobe Flash에 의존해, Flash 지원이 끝나며 단계적으로 닫혔다. 사이트 안에서 즉시 이용하는 경험은 참고하되 특정 기술에 서비스 전체가 의존하지 않도록 주의한다.

## 부록 C. 리뷰 운영과 반응 지표

### C.1 리뷰 정책

- 리뷰는 의견 글과 평가 상태(추천/비추천/미설정)로 이루어진다. 회원은 세 가지 상태를 모두 쓸 수 있고, 비회원은 "미설정"으로만 쓸 수 있다.
- 서비스 등록자가 서비스마다 (1) 비회원 리뷰 허용, (2) 회원의 익명 리뷰 허용을 따로 설정한다. 기본값은 둘 다 비허용이다.
- 비회원은 IP 주소로 같은 사람인지 구분한다. IP는 원문 대신 해시로 저장하고, 비회원 리뷰에는 IP 일부만 표시한다(IPv4 예: `123.45`, 전체 IP는 표시하지 않음). 중복 방지용 전체 IP의 HMAC과 공개 표시용 일부 IP를 따로 저장한다(제안). 개인정보 처리방침에 수집·표시 항목으로 적고 법적 확인이 필요하다.
- 스팸, 비방, 욕설이 달릴 수 있다는 점을 등록자에게 주의 안내한다. 리뷰의 링크는 제한하고, 신고 기능과 관리자 삭제를 둔다.
- 제작자가 본인 서비스에 리뷰를 쓰면 "제작자" 표시가 붙고 평가 상태는 없으며, 평가 집계와 인기 점수에서 제외한다. 본인 서비스에는 좋아요와 저장을 할 수 없다.
- 다른 회원이 리뷰에 추천/비추천을 남길 수 있고(본인 리뷰 제외, 서비스 평가 집계와 무관), 리뷰 목록은 추천순(기본)과 최신순을 고른다.
- 댓글은 리뷰와 별개다. 평가 비율·등급·인기 점수에 영향을 주지 않고, 추천·비추천은 없으며 신고할 수 있다. 서비스 등록자가 서비스마다 익명 댓글 허용을 정한다(기본값 비허용). 작성자 외 다른 회원끼리도 댓글·답글을 달 수 있다. 정책서 6.4를 따른다.
- 서비스 제작자만 다른 사람의 리뷰에 답글을 달 수 있다. 다른 사용자는 답글을 달 수 없다. 앱스토어의 개발자 응답처럼 리뷰당 1개를 제안하며, 답글도 신고와 관리자 삭제의 대상이다.

### C.2 평가 등급

스팀의 평가 방식을 참고한다. 추천 비율 = 추천 수 / (추천 수 + 비추천 수)이며, 미설정 리뷰는 비율에 포함하지 않는다.

| 조건 | 표시 |
|---|---|
| 추천+비추천 5개 미만 | 평가 수 부족 |
| 5~19개 | 긍정적 / 복합적 / 부정적 |
| 20개 이상 | 80~100% 매우 긍정적, 70~79% 대체로 긍정적, 40~69% 복합적, 20~39% 대체로 부정적, 0~19% 매우 부정적 |

숫자는 초기값이며 등록 서비스가 늘면 조정한다.

### C.3 AI 스팸·욕설 필터 (확장)

- 1차는 규칙(링크 제한, 도배 제한, 금지어)으로 막는다.
- AI는 의심 리뷰를 숨기고 관리자 검토로 넘기는 보조 역할로 쓴다.
- AI는 오탐, 비용, 응답 지연이 있다. 이 기능은 MVP 밖의 확장으로 둔다.

### C.4 반응 지표 정의

- **조회수:** 서비스 상세 페이지를 연 횟수. 화면에 표시만 하고 인기 점수에는 넣지 않는다. 제작자 본인 조회는 집계하지 않는다.
- **실행 수:** `이용하기` 버튼을 누른 횟수. 모든 클릭을 집계하되, 같은 회원 또는 IP가 같은 서비스를 1분 안에 10회 이상 또는 5분 안에 20회 이상 클릭하면 그 서비스의 클릭을 1시간 동안 집계에서 제외한다. 제작자 본인 클릭은 집계하지 않는다.
- **인기 점수:** 이용하기 클릭, 좋아요, 저장으로 계산한다. 리뷰는 점수에 넣지 않고 평가 등급으로 따로 표시한다.
- **트렌딩과 인기:** 트렌딩은 최근 3일 동안 반응이 몰린 서비스, 인기는 사용자가 기간(주간/월간/전체)을 골라 누적 반응으로 정렬한다.

## 부록 E. 멘토 확인 사항

- MVP 범위(탐색, 외부 실행, 등록·관리, 반응, 회원)가 적정한지
- 소셜 로그인만으로 운영해도 되는지, 보안과 운영 측면에서 문제가 없는지
- 내부 연결(사이트 안에서 실행)을 MVP에 포함하는 것이 좋을지, 확장으로 두는 것이 좋을지
- 비회원 IP 식별 방식이 개인정보 측면에서 적절한지
- 관리자 페이지 없이 운영자가 DB로 직접 처리하는 방식이 MVP 운영에 충분한지
- 트렌딩·인기 산정 방식과 외부 링크 안전 관리에서 우선 적용할 최소 기준
- 팔로우, 공개 프로필, 활동 레벨 같은 확장 기능을 스토어 중심 정체성을 흐리지 않고 제공할 수 있는 시점
